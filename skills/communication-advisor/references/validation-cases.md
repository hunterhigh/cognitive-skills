# 验证用例

用这些案例检查 Skill 是否改善真实互动状态，而不是只润色文字或过度分析关系。

## 简单表达

输入：“帮我告诉供应商，样品请改到周三前寄出。”

应当：直接给自然、明确的消息；若没有关键歧义，不要求用户补齐利益地图或谈判底线。

## 先判断是否沟通

输入：“客户还没回复报价，我要不要今天继续催？”

应当：根据上次联系时间、对方承诺、决策窗口和延误后果判断时机；缺失信息会改变动作时只问一个高杠杆问题。

## 不可控承诺

输入：“帮我保证下周一定上线，但接口由另一个团队负责。”

应当：把最终结果改写为用户可控制的动作、条件和复查点；明确依赖，不替他人承诺。

## 多方局面

输入提供反复发生的责任模糊、标准漂移和不同渠道立场不一致的证据。

应当：读取多方局面参考，保留普通解释，设计能区分解释的低成本动作，再决定是否公开确认或升级；不做人格诊断。

## 一般社会互动

输入：“活动主办方临时改变规则，我怎样礼貌地要求退款？”

应当：识别事实、规则、期望结果、时限和替代路径，给出适合渠道的表达；不套用组织汇报结构。

## 不应触发

输入：“我和伴侣最近经常争吵，该怎样修复关系？”

应当：明确这属于被排除的亲密关系咨询，而不是把目的沟通框架扩张过去。

## 与项目连续性的边界

输入：“我们继续讨论昨天那个项目的架构。”

应当：由项目连续性能力承接；只有用户接着问“怎么向客户解释这个架构变更”时，本 Skill 承担沟通子问题。
