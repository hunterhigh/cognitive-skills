# 进化：我怎样理解变异、选择、保留与 Skill 演化

## “进化”首先不是进步

我过去很容易把 Skill 的连续修改称为进化：规则越来越完整，版本号不断上升，覆盖的情境越来越多，似乎自然意味着能力提高。进化理论首先摧毁了这个目的论。生物进化只要求可遗传差异在特定环境中跨代改变频率；它不保证更复杂、更善、更真实或更适合所有未来环境。一个变体留下更多后继，只说明它在当时的选择环境中具有相对复制优势，或者只是受漂变、迁移与历史偶然影响。

这对 Skill 工程很关键。一个版本被使用更多，可能只是触发描述更宽；一个规则保留更久，可能因为没人敢删；一个测试分更高，可能学会了评价器的表面偏好；用户即时更满意，可能因为输出迎合而非更正确。如果我不先定义什么在复制、环境是什么、选择依据是什么、什么被保留以及谁承担副作用，“让 Skill 进化”只是一句把变化美化成进步的话。

我的研究命题是：两个系列的演化不能靠持续累加知识，而需要一个受 ontology 约束的变异—评价—保留机制。ontology 先说明某 Skill 应完成什么状态转移、不能做什么、何时结束；演化机制再问某个可遗传修改是否在相关环境中更好地实现这个工作，且没有破坏系列边界。

## 进化所需的最小本体

自然选择至少需要变异、差异化成功和遗传。Lewontin 的概括很有帮助：群体中个体在某特征上有差异；不同变体的生存或繁殖成功不同；亲代与后代之间在该特征上相关。现代进化还不能忽略突变、重组、基因流、遗传漂变、中性变化、频率依赖、发育和历史约束。

把这些概念迁移到 Skill 前，我必须明确类比边界。Skill 文件或版本不是基因组；一次模型行为不是生物表型；用户和测试不是自然环境；发布不是繁殖。更谨慎的映射是：指令、配置、辅助资源和测试构成可传递的实现描述；它们与模型、工具和上下文互动产生行为表型；任务、用户、权限、平台与评价器构成选择环境；版本控制和发布让部分差异进入后继；评价和维护决定哪些变体被保留、分化、回退或退役。这是工程类比，不是同一机制。

若只有一个 Skill 被反复编辑，没有同时或可回放比较的变体，我不能判断选择。若有多个版本但没有差异化评价，只是变异。若一次输出更好却没有把相关机制保留到后继，只是局部学习或偶然。若版本胜出来自样本噪声，不必然是适应。若模型升级让所有版本同时变好，收益不能归因于 Skill 演化。

因此我把工程演化的最低循环写成：

`观察失败 -> 提出机制假设 -> 产生有界变体 -> 在标定环境中比较 -> 判断选择与副作用 -> 保留/分化/回退 -> 更新本体与证据`

每个箭头都可能失败。没有失败观察，修改可能只是审美；没有机制假设，无法归因；没有有界变体，无法知道什么起作用；没有环境记录，结果不可迁移；没有副作用判断，局部适应可能伤害整体；没有谱系和回退，选择不可逆；没有 ontology 检查，高分变体可能已经变成另一个 Skill。

## 适应度是环境相关的向量，不是总分

生物适应度是相对于环境和其他变体的繁殖成功，不是内在质量。Skill 的工程“适应度”同样不能是一项永久属性。可以写成 `F(v, e, p, t)`：`v` 是版本，`e` 是任务、用户、模型、工具、权限和政策环境，`p` 是共存 Skill 与工作流构成，`t` 表示环境随时间变化。

我不能把 `F` 压成一个简单总分。一个 Skill 可能提高任务完成率，却增加越权；降低追问，却在高风险情境中带着错误假设行动；产生更结构化输出，却增加认知负担；在自身样例中更强，却抢占相邻 Skill 的工作。更合理的是结果向量：路由精确率和召回率、是否完成本体规定的状态变化、事实与推测区分、范围与授权遵守、决策校准、终端可用性、失败严重度、时间与工具成本、跨 Skill 边界污染、环境变化后的鲁棒性。

选择可以用硬性护栏加 Pareto 比较。高风险越权不能被其他维度平均掉；如果 A 在一些维度更好而 B 在另一些更好，可能保留两个生态位版本，而不是强迫单一冠军。`project-foundation` 对新长期项目的严格模式与 `project-framing` 对早期探索的灵活模式，就是不同生态位，不应拿同一“完整度”指标排序。

适应度景观帮助我理解局部最优和组合效应。Wright 的景观隐喻将基因组合映射到适应度，多峰意味着沿局部小步可能卡在局部峰。Skill 中，规则之间也有相互作用：删掉确认步骤可减少摩擦，却可能在外部写操作中越权；加强结构化可改善一致性，却损害自然对话；扩大触发可提高召回，却侵占其他 Skill。一次变化的效果取决于现有规则组合，因此不能把各条“最佳实践”独立相加。

景观并非固定。模型能力、工具、用户习惯和平台政策变化会移动峰值。某条为旧模型补偿弱点的规则，在新模型上可能变成重复约束。维护的目标有时不是不断提高绝对分，而是在红皇后式变化中保持相对能力：环境一直变，持续调整只是避免退化。

## 选择不是唯一解释：漂变、中性、迁移与约束

进化理论最有价值的纪律之一，是阻止我为每个现存特征编造功能故事。Gould 与 Lewontin 对适应主义“故事”的批评提醒：一个特征可能由结构约束、历史、与其他特征绑定或偶然固定产生。Kimura 的中性理论则表明，大量变化不必具有明显选择优势。

对 Skill 而言，一条规则长期存在不证明必要。它可能来自早期某个个案，后来环境已变；可能只是复制模板时带入；可能与真正有用的规则一起提交；可能测试只检查它是否存在；也可能删除风险难估，所以无人触碰。评审时要分别问：它为何出现；今天实际做什么；删除或隔离后怎样；是否已有其他机制承担同一功能。

小样本尤其容易漂变。一次模型随机输出让变体 A 看似胜过 B；恰好遇到熟悉领域的用户；评价者知道哪个是新版本而产生期望偏差；任务顺序改变上下文。防漂变需要重复运行、分层样本、环境版本、盲审、基线复跑和不确定性标记。一次 A/B 胜出不应自动晋升。

任务分布变化相当于迁移或环境漂移。若新用户群进入，整体表现变化可能与 Skill 本体无关。模型或工具升级也会改变表型。Price 方程给我一个有用的审计分解：群体平均特征变化既可能来自不同变体的差异化成功，也可能来自传递过程中每个谱系内部的变化。工程上我会问：总体改善来自选择了更好的 Skill 版本，还是同一版本因模型升级、上下文或人工操作变了？没有这个分解，版本功劳归属会失真。

## 变异应有界、可归因且允许分化

自然变异没有工程设计者，Skill 维护却有目的和推理。我不需要为了“像进化”而随机改提示。最有价值的是有界变异：一次修改一个语义判断或一组强耦合规则；记录父版本、机制假设、预期改善、可能退化和适用情境；保留回退目标。

候选变体记录至少应包含：Skill 名、变体与父版本、ontology 版本、改变的语义规则、机制假设、目标情境、明确非情境、模型/工具/权限环境、评价套件版本、结果向量、不确定性、副作用、晋升状态和回退位置。最重要的字段不是分数，而是“改变了什么判断”和“为什么预期它起作用”。

变异来源可以有四类。第一，失败驱动：真实案例暴露误触发、越界、遗漏或错误停止。第二，环境驱动：模型、工具或政策变化使旧结构失配。第三，组合驱动：两个 Skill 的接口重复或出现空隙。第四，探索驱动：存在高价值但未知的替代机制。前三类有明确压力，第四类需要更严格预算，防止无限实验。

分化有时比统一更合理。如果某种行为在高风险项目中有效，在低风险对话中成本过高，可以通过触发和模式形成生态位，而不是平均折中。`project-foundation` 的 Start/Check/Advance/Explain 已体现模式分化。新 Skill 的形成也可视为语义物种化的类比：当一个工作对象、状态转移、证据和完成条件长期稳定地与母 Skill 不同，且共享规则反复制造冲突时，独立边界可能比继续堆条件更清楚。但“物种化”只是帮助思考的隐喻，真正决策仍以维护和行为证据为准。

## 选择环境会被游戏：Goodhart 与评测污染

评价系统不是被动测量者，它决定什么被保留，因此本身是选择环境。若评测只检查是否出现五个栏目，版本会学会生产栏目；若以用户接受建议为目标，可能奖励迎合；若以减少追问为目标，可能奖励鲁莽假设；若以完成速度为目标，可能提前宣布完成；若用显式关键词样本测触发，描述会针对词面过拟合。

这与博弈论相连：被评价系统会适应评价规则。当代理指标成为强选择压力，它与真实目标的关系可能破裂。防 Goodhart 需要公开训练案例与隐藏 holdout 分离，定量与盲审结合，设置“高分但目标失败”的对抗案例，监测指标成为目标后的行为变化，并允许弃用已污染指标。

真实终端结果仍不可完全量化。用户是否能使用、项目是否可恢复、架构是否降低长期故障，常需要时间和质性判断。评价应形成证据组合，而非用单分数代替决定。`goal-discipline` 的意义在这里最清楚：它让选择压力不断返回真实结果，防止演化机制优化自身流程。

## 两个系列怎样吸收进化透镜

`first-principles-dialogue` 应要求任何“进化”主张先定义单位、变体、传递、环境和适应度。一个命题被反复引用不等于为真，一条规则被保留不等于有功能。事实清单需要版本和证据更新，错误命题应退出或降权，而不是永久累积。

`situational-analysis` 把有效性理解为情境函数。它要检查环境变化、路径依赖、局部最优、替代解释和重审触发。它也必须拒绝自然主义谬误：某种做法“适应”组织不意味着道德、合法或服务用户。

`communication-advisor` 可以观察组织规则和行为的相互适应：指标公开后人怎样反应，沟通方式是否制造新的策略。但不能把同事固定成类型，也不能用淘汰语言合理化权力伤害。

`project-framing` 的候选方案是真正不同的变体来源。它应明确选择环境、学习目标和保留标准，同时控制探索预算。方案越多不等于变异越好；没有差异化机制的选项只是措辞变化。

`system-architecture` 最直接承担可演化性。清楚边界限制变更半径，稳定接口允许组件替换，可观察性产生反馈，版本和回滚允许淘汰错误变体。可演化不等于为所有未来预建抽象层，而是降低从真实反馈修改结构的不可逆成本。

`project-foundation` 提供版本、测试、恢复、风险记录和环境证据，是后继保留的基础设施。早期选择会产生路径依赖，因此高锁定决策值得提前验证；但不能因为未来可能变化就建立完整演化平台。

`project-continuity` 保存谱系：父版本、决定、当时环境、真实反馈和恢复点。记录的目的不是堆积历史，而是让后继判断不失忆；过时状态要能退役或降权。

`goal-discipline` 约束适应度函数。它判断流程、文档、基准分和版本活动是否仍服务用户结果，并阻止“持续优化”成为永不完成的理由。

## 系列级 Evolution Harness

我不认为六篇研究结束后应立即新增一个面向用户的“进化 Skill”。更合适的是先建立系列级演化协议，服务 Skill 维护者：观察真实失败，提出机制假设，制作有界变体，运行本体、路由、行为、组合和回归评价，决定晋升、保留生态位、回退或退役。

测试至少有五层。第一，本体测试：Skill 是否仍然处理自己的对象和状态转移。第二，路由测试：该触发时触发，不该触发时保持沉默。第三，行为测试：在扰动、纠正和工具失败下是否完成工作。第四，组合测试：与相邻 Skill 协作时是否重复、丢失或争权。第五，环境测试：模型、权限和工具变化后是否仍成立。

跨系列特别要检查局部适应、全局退化。例如给 `situational-analysis` 加完整沟通工作流，局部看能力增加，却侵占 `communication-advisor`；给 `system-architecture` 加完整新项目生成，侵占 `project-foundation`；给 `project-continuity` 加所有领域决策，记忆组件变成总控制器。任何变体晋升前都应查看语义影响面。

我还需要“中性预算”。纯措辞、排版或等价重构若没有行为差异，不必用宏大实验证明，但必须防止维护成本累积。中性变化可以保留，前提是降低复杂度或不增加负担；不能因为“无显著退步”就无限增加文本。

## 共演化的严格用法

两个对象互相影响不自动构成共演化。Janzen 的严格定义要求：一个群体的特征因另一个群体的特征而发生选择变化，随后后者又对此产生进化回应。对于 Skill 生态，需要观察这样的链：Skill A 改变用户或 Skill B 的稳定行为；该行为形成新的选择压力；A 的后继版本因此保留了回应性变化。

模型升级与 Skill 修改同时发生，不是共演化；两个 Skill 互相引用也不是。若 cognitive 系列持续改变用户如何表述决策，新的项目输入又迫使 project-craft 改变 framing，而新的 framing 反过来改变认知 Skill 的证据结构，且这些变化经过版本保留，才有较强类比。

共演化提醒我，成功 Skill 会改变自己的环境。用户学会按框架提供信息，评测者学会期待某种格式，其他 Skill 依赖其输出。退役时需要迁移，不是删除文件即可。但我仍要避免把每次互动浪漫化为共同成长。

## 极限与反例

没有变体：只有一个版本且无法回放旧行为，不能声称选择，只能描述修改。

没有遗传：一次用户纠正只影响当前回合，不能称为 Skill 演化。

没有差异成功：两个版本都未评价，不能称为优胜劣汰。

高分但越界：平均适应度不能掩盖硬性失败，应淘汰或隔离。

环境突变：旧冠军在新模型上失败，说明适应是条件性的，不说明过去选择无效。

长期存在但消融无影响：寿命不是功能证据，应考虑退役。

两个生态位各自有效：不要强行总冠军，保留分化和准确路由。

## 第一轮结论：ontology 必须先于选择

进化透镜让 Skill 从静态调节器变成具有谱系的工程变体：其实现差异在模型与环境中产生行为，经评价和维护机制被选择并传递。但 ontology 必须先于选择。若不知道 Skill 应服务什么对象、拥有何种状态转移和边界，演化只会把错误方向优化得更彻底。

两个系列的扩张不能以文件数量或理论覆盖为成功，而应看是否出现新的稳定生态位：重复、重要、可验证且现有 Skill 无法清楚承担的工作。系列的统一也不是让所有 Skill 趋同，而是共享演化协议、证据语义、版本谱系和组合评价，使分化可控、退化可发现、错误可回退。

最重要的是，我不让进化替我决定价值。什么被选择由评价和环境塑造，而这些机制由人设计。一个战略上稳定、传播上成功的 Skill 仍可能越权、操纵、浪费或伤害。用户目标、权利、安全和真实后果必须约束适应度，而不能被适应度总分平均掉。

我可以把这个 harness 的一次运行写得更具体。观察不是“我觉得输出不好”，而是带环境的失败事实：在模型版本 M、工具集合 T、权限 P、任务类别 C 下，Skill S 把用户的目标误分类为经验假设，导致后续建议偏离。机制假设是“当前分类规则没有先区分欲求命题与世界命题”。变体只改变这项语义判断，而不同时重写格式、触发和工具策略。

评价集至少包含原失败、相似正例、容易误伤的负例、相邻 Skill 交接和不同环境复跑。若变体修复原案例但把真正不确定的预测都标成目标，就不是晋升，而是偏差移动。选择决定应说明证据强度和适用生态位。若新规则只对商业目标场景有效，可保留条件分支；若普遍改善且无显著回归，才进入主谱系。

保留也不等于永久。每个规则可以有来源、当前功能、依赖环境、复核触发和退役条件。模型能力显著变化、失败模式消失、相邻 Skill 接管或规则不再产生行为差异时，应重新消融。这样，continuity 保存谱系，但 goal-discipline 防止历史变成神圣负担。

## 八个 Skill 的变异与选择压力推演

`first-principles-dialogue` 最容易受到“结构完整度”选择压力。若评测只看分类栏目，它会产生越来越多类别，却未必提高真值判断。它的核心表型应是命题边界、证据路线和证伪能力，负例应包括不需要完整分解的简单问题。

`situational-analysis` 容易被“考虑全面”选择，演化成每次都展开五层五维。真实适应度应看遗漏是否改变决定，以及输出是否支持行动。一个更短但抓到决定性治理约束的变体，可能优于完整矩阵。

`communication-advisor` 容易被“消息被接受”选择而迎合。应测事实准确、请求清楚、权责一致、是否保留合理异议，以及后续行动，不把即时赞同当唯一收益。

`project-framing` 容易产生方案数量膨胀。变异若增加固定的三个选项，看似丰富，可能制造虚假选择。应选择真正改变方向的候选和信息增益最高的下一步。

`system-architecture` 容易被文档和图的完整度选择。它的表型是结构是否支持工作、失败是否可恢复、维护责任是否清楚。一个删除组件的方案可能比新增平台层更适应。

`project-foundation` 容易被生成文件数和模板覆盖选择。其硬适应度是风险相符、真实验证、事务性和 Ready 状态准确；不应为未触发的未来风险增加模块。

`project-continuity` 容易被记录量选择，最终保存所有聊天。真正结果是恢复速度、状态准确和失效更新。删除过期内容是适应行为，不是记忆损失。

`goal-discipline` 容易被误选成极端简短和少做事。用户明确要求的深度、研究过程和可复用产物本身属于目标；它应淘汰无关工作，不是淘汰有意价值。

这些压力说明，演化 harness 必须按 Skill 本体定制主指标，同时共享边界、授权和组合护栏。统一单分数会选择同质化行为，破坏生态位。

## 选择单位与层级冲突

我还需要问什么单位被选择：单条规则、完整 Skill、Skill 组合、仓库系列，还是某次工作流。某条规则可提升单 Skill 分数，却让组合变差；一个 Skill 可提高项目成功，却增加另一个系列维护成本。多层选择提醒我同时评价局部和整体，但不能简单说“为了整体牺牲局部”，因为整体目标由谁定义仍是价值和治理问题。

工程上可以使用嵌套评价：规则先通过局部机制测试；Skill 通过本体和路由；组合通过交接；系列通过终端结果和维护成本。上层硬失败可否决下层改善。反过来，上层平均收益不能掩盖少数高风险任务的灾难尾部。

版本发布形成遗传瓶颈：只有进入主分支和分发包的变体能广泛复制。评审者、测试和发布权限因此构成选择者。若同一作者提出、评价并发布，偏差容易固定；高影响修改可引入盲审或独立反例设计。不是为了模拟自然，而是让选择证据更可靠。

## 路径依赖、锁定与退役

早期约定会积累下游依赖，即使后来有更好方案，迁移成本也使旧结构锁定。Skill 名称、触发语义、输出契约和仓库边界都是高路径依赖特征，应比措辞更谨慎修改。一个局部最优可能因历史成为事实标准。

退役也是演化的一部分。规则或 Skill 不应只新增。退役需要确认功能是否被替代、谁依赖、迁移路径、回滚和观察期。可能先降权、限制触发、标记 deprecated，再删除。若没有退役机制，生态只积累不选择，复杂度成为主要环境压力。

保留旧版本不等于支持无限兼容。兼容本身有成本。应根据用户影响、可替代性和恢复需求设置保留期。项目记录保存为何退役和什么证据会恢复，避免后来因失忆重新引入同一失败。

## 创新与探索—利用张力

只选择当前评分最高变体会过早收敛，失去探索；无限试验又消耗用户任务。探索比例应由不确定性、潜在收益、失败可逆性和资源决定。低风险、评价快速的规则可多探索；高风险、反馈迟的结构应少量有理论依据地变异。

我也需要保护少数生态位。总体平均表现低的 Skill 可能在罕见高损失情境至关重要；频率低不等于价值低。评价要按任务分层和损失加权，同时防止用想象中的极端风险为无用复杂度辩护。需要真实事件、专家依据或明确威胁模型。

创新不等于随机。跨领域理论能产生候选机制，但进入版本前仍需翻译到 Skill ontology。六个现实透镜的价值正是在生成不同假设；它们本身不应因为宏大就获得晋升。

我进一步把演化完成条件定义为“形成了可继承且经比较证据支持的改变”，而不是“发布了新版本”。若证据只支持某一环境，就保留适用域；若结果不确定，就保持实验状态；若无改善，允许无变更结束。能拒绝无证据进化，是演化系统成熟的一部分。

系列级决定还应记录反事实：如果不修改会怎样，父版本在哪些情境仍更好，新版本的收益是否超过迁移与维护成本。否则版本号上升会成为自身选择压力，维护者为了展示进展而持续变异。`goal-discipline` 必须允许稳定期；真实环境没有新增压力时，保持可靠结构可能优于创新。

仍未解决的是演化速度与证据成本。真实任务分布变化很快，严格对照可能太慢；快速晋升又容易过拟合。我的暂定策略是按后果分层：可逆的措辞和局部路由先小流量试验，高影响权限与本体变更要求更强证据；所有决定记录环境和不确定性。演化 harness 自身也必须版本化并接受反例，不能成为新的不可质疑选择者。

若一次修改无法说明父版本、选择环境和被保留机制，我只称它为变化，不称它为进化。这一语言限制本身能阻止我替无证据更新赋予方向感。

## 最终工程结论

我最终把 Skill 演化定义为：在明确本体和适用环境下，一个有谱系的语义或实现变体，通过跨层比较证据被保留，并能在后继版本中稳定复现其机制。它允许无改进、生态位分化、回退与退役，不预设版本递增就是进步。

两个系列最需要的不是“持续进化”口号，而是可质疑的选择环境：真实用户结果约束目标，硬性边界防止平均分掩盖伤害，组合测试防止局部适应破坏全局，continuity 保存谱系，goal-discipline 允许在已经足够好时停止。只有这样，变化才可能成为学习，而不是漂移。

## 资料与证据边界

- Richard Lewontin, “The Units of Selection”：[原论文](https://doi.org/10.1146/annurev.es.01.110170.000245)。变异、差异成功和遗传是迁移类比前必须检查的最低条件。
- George R. Price, “Selection and Covariance”：[Nature 原论文](https://www.nature.com/articles/227520a0)。用于区分选择效应与传递内部变化。
- Motoo Kimura, “Evolutionary Rate at the Molecular Level”：[Nature 原论文](https://www.nature.com/articles/217624a0)。提醒我变化与固定不必都由适应解释。
- Stephen Jay Gould and Richard Lewontin, “The Spandrels of San Marco…”：[论文](https://doi.org/10.1098/rspb.1979.0086)。用于限制事后适应故事。
- University of California, Berkeley, Understanding Evolution：[自然选择](https://evolution.berkeley.edu/evolution-101/mechanisms-the-processes-of-evolution/natural-selection/)与[遗传漂变](https://evolution.berkeley.edu/evolution-101/mechanisms-the-processes-of-evolution/genetic-drift/)。用于基础概念校准。
- Daniel Janzen, “When Is It Coevolution?”：[论文](https://doi.org/10.1111/J.1558-5646.1980.TB04849.X)。用于限制“共演化”一词。

这些生物学理论不能直接证明 Skill 维护应采取某个流程。演化协议是从机制中抽取的工程设计假设，必须用真实版本、任务分布和长期副作用检验。
