# 六个现实透镜：阅读反馈与结构修正记录

这份记录保存用户逐篇阅读后的反馈、我对反馈的当前理解、因此发生的结构修正，以及仍待确认的问题。它不是对原话的总结替代；原始反馈优先于我的解释。讨论成熟后，再决定是否修订正文或实际 Skill。

## 总论研究校正 01

记录时间：2026-09-21

用户对十个研究问题作出根本校正：

1. 在理性环境下，应假定现实问题存在一个受约束的最优解；这个最优解不只服务“用户相对别人获胜”，而应同时服务用户、其过去与未来状态、所处环境、相关他人以及相对于不行动基线的整体结果。
2. “争取优势”与“避免劣势”不应被预先建模成需要用户选择优先级的两个竞争目标。若研究充分，风险、损失、无知、混乱、机会与收益应在同一个最优解中被共同处理。
3. 不应先按项目、商业、人际、学习、消费等领域切割“任何情境”。研究对象是跨情境成立的现实判断与行动结构，具体领域只作为运行时情境和验证样本。
4. 不应依赖用户先提供三个失败故事才开始建立本体。真实经验后续可作为证据和校正，但基础结构应先从现实原理与可证伪命题推导。
5. 体系将持续跟随用户、环境和实际结果迭代；它不是一次性方法、静态用户画像或固定项目配置。
6. “系统级主控 Skill”不是必要结构。此前把用户关于语义基础的反馈过早编译为中央主控，是未经验证的设计跳跃；后续研究撤销该前提。

由此，系统篇反馈 01 中“系统主控”“配置编译器”等内容降级为已被否定的候选方案，只保留为错误路径记录，不再作为后续文章或 Skill 体系的架构前提。仍可能需要共同语义、兼容关系和评价证据，但它们可以由分布式约定、组合关系、运行时判断或其他尚未涌现的结构承担。

新的研究起点是：

`在现实约束、相关主体与时间范围内，寻找能够最大化整体有效收益、同时吸收可预见损失与不可逆风险的行动结构，并让该结构依据新证据持续修正。`

这是待研究命题，不预设最终必须形成中央 Skill、固定流水线、单一效用函数或静态最优策略。

## 总论研究校正 02

记录时间：2026-09-21

在第二章草稿中，用户说“优化目前的六个 Skill”，随后明确校正：数量可能记错，研究和优化对象始终是 Cognitive Skills 与 Project Craft 两个系列的全部 Skill。

我曾把“六个”过度解释为用户可能在区分六个核心能力与两个横向能力。该解释没有用户证据，已撤销。当前两个仓库共八个 Skill，全部属于优化范围：

- Cognitive Skills：`first-principles-dialogue`、`situational-analysis`、`communication-advisor`；
- Project Craft：`project-framing`、`system-architecture`、`project-foundation`、`project-continuity`、`goal-discipline`。

根据实际职责，仍可把其中六个暂称为对象型状态转换器、两个暂称为运行型状态转换器，但这只是一项待验证的架构假说，不能由用户的数量口误推出，也不能降低后两个 Skill 的优化优先级。后续评价应允许该分类因路由、实测或用户反馈而被推翻。

## Skill 优化校正 01

记录时间：2026-09-21

用户基于日常使用，对第二章的候选优化作出以下校正：

1. `first-principles-dialogue` 应是完全的思考类 Skill，不需要 SMART、商业目标等应用内容。
2. 第一性原理不应先确定命题。它从原子事实拆解、数理关系与其他信息提取开始，再由这些要素组合复杂命题。现有 Skill 确实过于宏大，且架构不符合用户的日常使用。
3. `situational-analysis` 当前方向可以继续。
4. `communication-advisor` 的本体是沟通中的顾问，可以升级为更通用的沟通咨询入口，而不只限定工作关系。
5. `project-framing` 与 `system-architecture` 的候选优化方向可以继续。
6. `project-continuity` 的主要用途是通过开会帮助用户建立工作节奏；它是用户日常高频 Skill，应成为 Cognitive Skills 与 Project Craft 的协作入口，也是想法发生和逐步形成的地方。它不能被主要理解为记录与恢复机制。
7. `goal-discipline` 是最小原则构造，用来收敛大模型输出，使其专注当前任务，抵抗为了完整性胡乱覆盖各种情况的倾向。它不应扩张成复杂的优势评价框架。

因此，第二章中以下候选判断暂时失效：把第一性原理写成“定题—拆分—检验—重组”；把项目连续性的核心描述为反馈和恢复通道；给目标纪律增加较多状态贡献、选择权或可行性判断。后续讨论需要重新确定第一性原理的生成方向、通用沟通顾问的范围，以及以会议节奏为核心的连续性入口怎样与其他 Skill 协作而不成为中央主控。

## Cognitive 分析双 Skill 决定 01

记录时间：2026-09-21

用户进一步确认：

1. 第一性原理从六门学科的综合认识中寻找原子事实、数理关系与复杂命题生成方式，不以前置命题限制发现。
2. 通用沟通顾问不扩展到亲密关系、家庭和朋友关系咨询；其通用性仍有明确社会与任务边界。
3. `project-continuity` 必须在已有项目中运行，是项目层的高频工作 Skill，通过开会建立节奏、孕育想法，并作为 Cognitive Skills 与 Project Craft 在项目协作中的入口。
4. 现有 `situational-analysis` 与一个新的战略认知 Skill 应成为几乎平行、可以日常同时调用的能力。前者判断方案在当前现实中是否成立，后者从系统、控制、博弈、进化、维护成本与价值条件分析局势怎样变化，以及怎样帮助用户形成和保持更有利轨迹。

命名决定：不采用缺乏路由语义的 `analysis1` / `analysis2`，将原 `situated-decision` 更名为 `situational-analysis`，新增 `strategic-analysis`。二者可以共同工作，但不形成固定先后流水线，也不构成系统级主控。

## 战略定义校正 01

记录时间：2026-09-21

用户用国际象棋开局说明战略与优势的时间关系：开局存在大量模式，第一步通常不会立即展现一个已经兑现的明显优势；但以赢得整局为时间范围，开局会建立后续获得优势的条件。因此策略确实用于获得优势，但不能把优势狭义理解为当前一步的即时收益。

据此，`strategic-analysis` 将策略定义为：在相关时间范围内，根据状态、反馈和他方回应选择并组织行动，以创造、积累、保持或兑现优势条件的连贯政策。分析区分即时优势、位置优势、动态优势与终局优势，并要求说明各层之间的转换机制、阶段信号、合理时间范围和停止条件。这样既不以短期收益淘汰所有布局，也不允许用“长期优势”保护无法证伪的无效行动。

## 情境分析核心校正 01

记录时间：2026-09-21

用户确认 `situational-analysis` 应以五层五维为主要核心，其主要价值是保证问题观察与判断的全面性。五层是信息、逻辑、系统、人性、意义，用于纵向深化判断依据；五维是时间、利益、治略、博弈、哲理，用于横向扩展观察范围。

情境认知、有限理性、探究和决策分析只能作为五层五维的理论加固，不能取代主本体或把 Skill 改造成通用决策分析。主文件据此重构为五层 × 五维的情境坐标系，以发现会改变结论、取舍和行动的决定性遗漏为完成标准；不要求输出二十五格矩阵，也不以篇幅代表全面性。

## 系统篇反馈 01

记录时间：2026-09-21

### 用户原始反馈

1. “系统这一部分我感觉我意识到我们需要一个系统级别的主控系统来作为不飘逸的语义基础，这个语义是链接所有skill的大前提，其实本身是希望通过”
2. “你目前的这个说法是有道理的，但是从工程来说，又需要考虑灵活性。我觉得项目级skill的配置会更像一个封闭系统，但是一个系统级别的skill会更像一个通用性极强的方法论基座。这一部分的缺少讨论，让你对skill的思考还需要注意”
3. “评价分层我能理解，但是如果工程化？工程化会是什么样子？”
4. “是的这个也是，这个该如何工程化？”
5. “这个该如何工程化？”
6. “宏大统一的错误是你需要注意的，你需要思考，你总数喜欢做加法。”

注：第 1 条原句停在“希望通过”，目前按未完成句保留；第 4、5 条缺少被指代的原段落。结合系统篇上下文，暂分别映射为“差分演化证据如何工程化”和“共享能力不等于共享文本如何工程化”，等待用户后续校正。

### 我接受的批评

原系统篇为了防止产生吞并所有工作的超级 Skill，过度强调去中心化、近可分解和最小协议，因而没有充分讨论另一项同样真实的需要：如果各 Skill 没有共同的语义根，它们的触发、状态、证据、权限、交接和完成含义会持续漂移。只有局部自治，没有系统级语义控制面，并不能形成一个可演化的 Skill 系统。

“系统级主控”不能被简单否定为宏大统一。需要区分两种中央化：

- 错误的中央化：一个超级 Skill 吞并所有领域判断、工作流程和输出，成为新的复杂单体。
- 必要的中央化：一个语义控制面规定最小共同 ontology、Skill 合同、状态协议、路由与评价语义，使局部 Skill 可以自由演化而不失去系统一致性。

因此，原文“统一对象是共享语义协议，而不是总 Skill”还不够。更准确的说法是：共享语义协议需要一个能够解释、实例化、检查和演化该协议的系统级能力。它不是被动词典，而是方法论基座与控制面。

### 新的系统结构假设

系统级结构暂写为：

`开放方法论基座 + 项目情境 + 可用 Skill 合同 + 项目约束 -> 项目级 Skill 系统配置`

系统级基座保持开放和通用，项目级配置则相对封闭、可复现、可评价。二者不是对立，而是编译关系：

1. **系统语义核**定义跨 Skill 稳定概念，如目标、事实、假设、状态、证据、权限、动作、交接、完成和重审。
2. **Skill 合同注册表**说明每个 Skill 接受什么状态、完成什么变换、产生什么状态、排除什么、需要什么权限、何时完成。
3. **项目配置编译器**把通用语义、项目目标、风险、可用环境和启用的 Skill 编译成一个带版本的项目运行配置。
4. **系统主控**读取当前项目状态，选择当前状态变化的所有者，装配必要辅助能力，检查交接和停止；它不替代局部 Skill 的领域判断。
5. **评价与演化装置**用同一语义记录实际轨迹、终端结果、失败类型和版本差异，再决定局部修改还是系统关系修改。

这里的“封闭”不是物理隔绝，而是：一个项目版本中的目标、可用 Skill、权限、约束、状态协议和评价标准被固定下来，使运行可复现。这里的“开放”也不是无限扩张，而是：系统级基座允许注册新 Skill、新项目类型和新证据来源，不要求修改所有既有 Skill。

### 最小工程对象

暂不建立多个新 Skill。先验证四种可落地对象是否足够：

#### 1. `SystemOntology`

版本化的语义规范，至少区分：

```text
Purpose
Fact / Assumption / Goal / DesignChoice / ResearchQuestion
State / Observation / Model
Actor / Authority / Constraint / Resource
Action / ExpectedTransition / ActualTransition
Handoff / CompletionCondition / RevisionCondition
```

它定义语义和兼容规则，不规定所有 Skill 必须采用同一输出格式。

#### 2. `SkillContract`

```text
skill_id
ontology_version
accepts
transforms
produces
excludes
reads_state
writes_state
authority
required_evidence
completion
invalidated_by
handoff_contracts
```

这个合同是系统级主控理解局部 Skill 的接口；Skill 内部仍可采用自己的方法。

#### 3. `ProjectSkillProfile`

```text
project_id
profile_version
purpose
system_boundary
enabled_skills
project_constraints
authority_map
state_store
routing_overrides
evaluation_policy
extension_points
```

它是从开放方法论基座编译出的相对封闭项目配置。修改配置要产生新版本；运行时不能悄悄改变语义。

#### 4. `WorkTrace`

```text
input_state
selected_owner_skill
supporting_skills
observations_used
decision_or_action
output_state
handoff
terminal_outcome
failure_class
environment_version
```

它给评价和演化提供共同证据，但不要求暴露模型的私密思维过程；记录的是可审计的状态、证据、决定和结果。

### 分层评价如何工程化

评价层不是几组抽象指标，而是同一 `WorkTrace` 在不同边界上的可执行测试：

1. **L0 合同层**：静态检查 SkillContract 是否完整、类型是否有效、读写状态和权限是否冲突。
2. **L1 Skill 层**：隔离运行单个 Skill，测试它是否在适用情境完成自己的状态变化，并在非情境保持沉默。
3. **L2 接口层**：运行两个或多个 Skill 的交接案例，检查事实是否被降级或升级、假设是否被误当决定、状态是否丢失、责任是否重复。
4. **L3 项目任务层**：在一个版本化 ProjectSkillProfile 中运行端到端情境，检查用户要求的终端状态是否实现，而不是所有步骤是否出现。
5. **L4 系统层**：跨项目和跨版本查看路由冲突、总体成本、失败尾部、恢复能力、维护负担和环境变化鲁棒性。

每层都有 fixture、runner、assertion 和 result，不用一个总分掩盖硬失败。评价结果是向量，权限越界、事实伪造或不可恢复损害属于否决项。项目级指标可以灵活配置，但它们必须映射到系统语义核，才能跨 Skill 解释。

### 差分演化如何工程化

每次修改建立一个 `SkillVariantEvidence`：

```text
parent_version
changed_semantic_rule
observed_failure
mechanism_hypothesis
intended_context
explicit_non_context
affected_contract_fields
baseline_results
variant_results
adjacent_skill_regressions
system_level_side_effects
promotion_or_rollback_decision
```

执行顺序是：真实失败进入 → 判断失败属于局部 Skill 还是系统关系 → 制作最小变体 → 重放原案例与负例 → 运行相邻接口回归 → 在项目配置中试验 → 晋升、保留生态位或回退。没有父版本、机制假设和比较证据的修改只叫变化，不叫演化。

### “共享能力不等于共享文本”如何工程化

共享内容分成三种，而不是复制同一提示：

- **语义共享**：由 SystemOntology 和 SkillContract 维护。
- **行为共享**：由 conformance tests 检查，例如所有 Skill 都不得把目标当事实、不得越过权限、必须说明完成条件。
- **实现局部化**：每个 Skill 保留自身判断程序、案例和输出，不依赖一个庞大公共 prompt。

两个仓库初期不建立共享运行时代码依赖。先共享版本化规范、机器可读合同与兼容测试。只有当重复解析、验证或路由逻辑造成真实维护问题时，才抽取小型工具。这样保留独立复制和发布，又能避免语义漂移。

### 对“总喜欢做加法”的约束

系统主控的准入原则不是“看见缺口就新增层”，而是先做减法：

1. 能否删除重复规则解决？
2. 能否澄清现有 Skill 合同解决？
3. 能否增加一个接口或测试解决？
4. 只有存在新的、稳定的系统级状态变化时，才增加新能力。

系统级基座只拥有四类职责：共同语义、配置编译、运行协调、系统评价。领域知识、局部判断流程、项目具体目标和用户决定不进入主控。任何新增字段或组件都必须指出它修复的失败案例；没有行为差异就不加入。

### 当前未决

- 第 1 条“其实本身是希望通过……”的完整意图仍待用户续写。
- 第 4、5 条的确切指代仍待用户确认；当前工程回答只是基于上下文的暂定映射。
- 系统级主控最终应是一个 Skill、一个 harness、一个规范包，还是三者组合，尚未决定。应先用合同、项目配置和分层评价的最小原型验证，再决定物理形态。
- “项目级封闭”的具体程度需要继续讨论：是每个仓库固定，还是每个项目/阶段生成一份 profile；过度封闭会损失临场适应，过度开放又无法复现。
