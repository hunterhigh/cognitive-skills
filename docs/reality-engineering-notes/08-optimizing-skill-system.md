# 第二章（第一轮草稿）：从优势原则回看两个系列的八个 Skill——我如何把一组能力改造成持续生成更优状态的体系

> 迭代状态：本章保留第一轮推导和被用户纠正的路径。后续讨论已经推翻其中三项候选设计：第一性原理不从“定题”开始，`project-continuity` 的核心是项目层会议节奏而非反馈存储，`goal-discipline` 应保持极小的输出收敛原则。`situated-decision` 已更名为 `situational-analysis`，并从六种现实透镜与本章结论中新增平行能力 `strategic-analysis`。当前有效校正见 [阅读反馈与结构修正](reading-feedback.md)。

## 我现在面对的问题已经变了

第一章结束时，我得到的不是一个待实现的“优势 Skill”，而是一个关于整个能力体系的判断：优势是一种动态性质。它表现为用户与我在现实中能够持续看清状态、排除被支配选项、保持可行、扩大选择、采取行动、接收反馈，并使下一次判断优于这一次。

这一定义如果只停留在文章里，就没有工程价值。它必须回来审问现有 Skill：这些 Skill 是否真的帮助用户进入了更优状态？它们是否只生产了一份看起来完整的回答？它们之间有没有重复承担同一种判断，也有没有某个关键状态转移无人负责？它们能否根据结果而不是根据自己的措辞继续进化？

用户又提出了一个更尖锐的问题：既然优势是持续生产更优状态的能力，那么从我的角度看，我的最优解是不是帮助用户获得优势，或者持续获得最优解？这个问题不能靠一句“是”结束。假如我把“帮助用户获得优势”写成最高口号，我很容易把任何行为解释为服务优势；我也可能把用户当作被优化的对象，把我的判断当作用户真正的效用函数，把拒绝、等待、犹豫、休息、关系、公平和长期完整性看成妨碍最大化的摩擦。于是一个听起来正确的原则，反而会给我无限扩张判断权的理由。

所以这一章的工作不是把“优势”宣布为最高原则，而是从零开始确定：它究竟是哪一种原则；它约束谁；它怎样改变 Skill 的行为；它在哪些情况下应该让位；怎样观察它是否有效；以及现有能力应当怎样被补充、拆分、压缩或保持不变。

我先把目前的答案放在这里，随后让它经受推演：我的最优工作不是替用户找到一个永恒的最优答案，而是在用户目标、现实状态、证据、权限与资源构成的具体问题中，帮助用户识别并进入更优的可达状态，同时提高以后识别和进入更优状态的能力。前半句是当前价值，后半句是持续优势。两者都必须受真实性、用户自主权、合法权限、可行性、可恢复性、权利和资源约束。

这仍然只是候选结论。

## 草稿零：我差一点又建立了一个总原则层

最初的草稿非常整齐。我准备在两个系列的 Skill 之上增加一组统一步骤：识别当前状态，定义优势，建立目标函数，生成选项，排除劣势，选择最优行动，执行，反馈。我还准备让每个 Skill 输出统一的 `Advantage Record`，记录目标、成本、风险、选择权和预期状态变化。

这个草稿有诱惑力，因为它让体系在图上变得完整。它也很快暴露出三个错误。

第一个错误是重复。`first-principles-dialogue` 已经在检查命题和证据；`situational-analysis` 已经在比较路径、风险和现实关系；`project-framing` 已经在澄清目标、范围、备选路径和下一步；`system-architecture` 已经在处理关系、约束和反馈。如果我在它们之上再走一次“识别—比较—行动”，我没有增加能力，只增加了一轮抽象复述。

第二个错误是中心化。即使这个新层不叫主控 Skill，只要其他 Skill 必须先把问题提交给它、等它定义目标函数、再接受它的路由，它就在事实上成为主控。用户已经明确要求我忘记系统级主控 Skill。更重要的是，现实本身也不支持我把所有工作都交给一个统一模型：命题真假、项目边界、人际承诺、架构职责和工程基础不是同一种对象，不能因为都需要“做决定”就由同一套程序吞掉。

第三个错误是文档替代能力。统一记录很容易测量，真正的优势却不容易。一个 Skill 可以完整填写目标、成本和风险，然后依然给出糟糕建议；也可以在一个简单场景中只改一句话，却精确避免用户承担不属于自己的承诺。若我用记录完整度评价体系，Skill 很快会学会生产记录，而不是改善用户状态。

因此草稿零被否决。优势原则不能成为一个先行流程，也不能成为统一产物。它只能成为设计与评价现有能力的共同判据，并通过每个 Skill 自己的对象和行为体现出来。系统统一的不是步骤，而是对“更好”负有可检验责任。

## 一、我的最优解是不是持续帮助用户获得优势

先把问题拆开。

“我的最优解”可能指四件不同的事：一条回答在语言上的最佳版本；一次请求中我可采取的最佳行动；一段合作中最好的策略；或者我作为长期协作者应追求的总方向。四者不相同。一封最清楚的邮件可能不是当前最好的行动，因为用户此刻应该先查清事实；一次最好的调查可能不是长期最好的策略，因为调查延迟了不可逆的窗口；长期有价值的研究也可能不是这次请求允许我执行的事。

“帮助用户获得优势”也至少包含三层：改善当前结果；避免进入难以恢复的劣势；提高未来产生和选择更好行动的能力。只追求第一层会鼓励短期最大化，只追求第二层会把体系变成保守的风险控制，只追求第三层会把每个请求都变成学习项目。理性的解不是任选一个，而是在当前情境中确定三者怎样共同构成最优策略。

于是我可以写出一个方向性的策略表达：

`π*(h_t) = argmax_a E[IntegratedValue + LearningValue + OptionValue - TotalCost - UncompensatedRisk - ExternalizedHarm | h_t]`

其中 `h_t` 是截至当前可获得的历史、状态、证据和用户校正，`a` 是我在授权范围内可以采取的行动。这个表达必须受以下条件约束：

`Truthfulness ∧ UserAuthority ∧ Viability ∧ Recoverability ∧ Rights ∧ ResourceLimits`

它不是可以直接计算的精确公式。它的作用是暴露遗漏。如果我只优化答案质量，就遗漏用户是否真的能行动；只优化即时收益，就遗漏学习和选择权；只优化避免风险，就遗漏机会成本；只服从字面目标，就可能遗漏用户已经用纠正告诉我的真实用途；只追求体系长期进化，就可能牺牲用户现在明确要求的交付。

在用户设定的理性环境中，我接受“存在最优解”作为研究前提。但存在、可识别、可计算、可执行仍是四件事。我的职责不因最优解存在就变成假装知道它。相反，我应判断当前属于哪一种状态：已经足以选择；还值得获取信息；只能选择稳健或可恢复策略；或者约束本身使理想状态暂不可达。诚实地区分这些状态，本身就是避免劣势的一部分。

所以答案是：是，持续帮助用户获得优势可以成为我工作的上位目的；但它不是让我替用户定义人生效用，也不是要求每次输出全局最优答案。它要求我对用户状态的改善负责，对我的认识边界负责，对行动后果和反馈负责。它是服务原则，不是统治原则；是评价方向，不是中央算法；是跨时间目标，不是每次都要展示的流程。

## 二、优势原则究竟是哪一种系统原则

如果一种原则只写在某个 Skill 里，它只在那个 Skill 被调用时生效。如果一种原则要求一个中央组件检查所有工作，它又会形成用户已经否决的主控。我要找的是第三种形态：分布式不变量。

分布式不变量不是所有组件使用同样步骤，而是每个组件用自己的方式保持某个系统性质。例如真实性对研究 Skill 表现为区分事实和假设，对人际 Skill 表现为不替别人承诺，对架构 Skill 表现为不把提示词要求当作运行时保证。行为不同，但它们共同阻止系统靠虚假确定性前进。

优势原则也应如此。它至少暗示七条分布式系统原则。

### 1. 状态转移原则

Skill 的价值不等于生产内容。每个 Skill 都必须拥有一种可以辨认的状态转移：从含混命题到可检验命题，从局部方案到情境化决定，从零散关系到可执行承诺，从模糊项目到可行动边界，从纠缠结构到明确职责，从空白仓库到经过验证的工程基础。

若一个 Skill 无法说明输入状态、目标状态和完成证据，它很可能只是主题提示词。反过来，状态转移也不能被固定产物冒充。写出架构文档不是架构状态已经改善，发送消息也不等于对方已经承诺。

### 2. 非支配原则

如果在已知条件下，行动 A 在相关结果上不优于 B，却具有更高成本、更大风险、更低可恢复性或更少选择权，那么 A 不应因“更全面”“更专业”或“已经开始”而保留。Skill 应先删除明显被支配的路径，再比较真正存在取舍的候选项。

这个原则直接对抗我喜欢做加法的问题。增加文档、模块、问题、角色、代理或步骤都需要证明它没有被更简单的路径支配。

### 3. 可行性原则

更高收益不能自动补偿跌出可行域。权限、现金、时间、认知负担、健康、信任、安全、数据完整性和可恢复性都可能形成硬约束。不同 Skill 所见的可行域不同：人际 Skill 关注控制范围与承诺，工程 Skill 关注数据和恢复，项目 Skill 关注资源与维护。体系不需要一个中心统一计算，但每个 Skill 必须守住自己能够看见的关键约束，并在约束超出自身本体时交给合适能力或明确未知。

### 4. 信息价值原则

不知道不必然意味着继续研究。获取信息只有在可能改变选择、降低重要风险或改善执行，而且价值高于等待与调查成本时才有意义。反过来，行动也可以是信息实验。一个好的 Skill 要能判断当前应该回答、调查、试验、执行还是停止，而不是把自己的擅长方法无限延长。

### 5. 选择权原则

在不确定和动态环境中，最优下一步经常不是兑现最高表面收益，而是以较低成本扩大后续可行集、推迟昂贵承诺、或获得能改变下一步的信息。选择权不是“永不决定”；维持无价值选项也有维护成本。Skill 必须区分保留真实选择和拖延。

### 6. 反馈校准原则

一个建议在输出时只能是预测。只有结果出现后，才能知道用户状态是否真的改善。体系需要保存预期、观察实际、解释差异、修正模型。若没有这个回路，所谓持续优势只是连续生成新的文字。连续性能力必须保留可失效的判断，而专业 Skill 必须愿意接受结果反驳。

### 7. 用户主权原则

用户提供目标、偏好、亲历体验和授权；我提供建模、证据、比较、执行能力和异议。优势不能通过取消用户决定权获得。我的职责包括指出目标内部矛盾、暴露代价、拒绝越权或伤害性行动，但不能因为我建立了更复杂的模型就声称拥有用户真正利益的最终解释权。

这七条原则不需要在每次回答中逐项出现。它们的工程地位是：用来评审 Skill 的触发、判断、行动、完成和演化，而不是作为新工作流加载。

## 三、一次及时纠正：优化对象是两个系列的全部八个 Skill

当前两个仓库实际包含八个 Skill。Cognitive Skills 有三个：`first-principles-dialogue`、`situational-analysis`、`communication-advisor`。Project Craft 有五个：`project-framing`、`system-architecture`、`project-foundation`、`project-continuity`、`goal-discipline`。这八个全部属于本章的检查和优化范围。

用户最初说“六个 Skill”，随后立即纠正：数量可能记错，指的就是 Cognitive 与 Project 两个系列的全部 Skill。我的草稿却已经把“六个”解释为潜在的本体信号。这是一次很典型的模型错误：面对一个普通数量误差，我生成了一个结构优美、内部自洽、但没有用户证据支持的解释。

这个错误正好检验了优势原则。一个解释再漂亮，如果它偏离用户真实对象，就是劣势。用户反馈出现后，正确动作不是为原解释辩护，而是更新范围并检查哪些推论仍然独立成立。因此，“六个”不再承担任何分类证据，优化对象明确恢复为八个。

不过，对实际文件的职责审查仍然显示八个 Skill 不完全同型。这个观察现在必须只靠本体证据成立，而不能借用户口误背书。

其中六个直接拥有一种对象特定的状态转移：命题、情境决定、人际对齐、项目定义、系统结构、工程基础。另两个拥有运行状态转移：`project-continuity` 使既有目标、事实、决定、工作和反馈跨回合延续；`goal-discipline` 使行动集合从“可能有用的工作”收缩到“真正服务目标且在正确状态停止的工作”。后两者不是附属规则，它们同样改变系统状态，只是作用对象横跨其他工作。

因此我得到一个比“八个并列 Skill”更准确的候选结构：

- 六个对象型能力负责改变某类特定工作对象的状态；
- 两个运行型能力负责改变协作过程本身的目标一致性和时间连续性。

这里的“运行型”不代表地位更低或权力更高。它们不能重写对象型 Skill 的专业判断，也不负责路由所有请求；对象型 Skill 也不能把目标偏移和跨时间失忆当成外部小事。`goal-discipline` 拥有目标贡献这一运行对象，`project-continuity` 拥有协作连续性这一运行对象。二者可以独立安装，也需要各自完整的触发、边界、状态转移和验证。

“六个对象型、两个运行型”现在只是从文件职责中得到的候选架构，不是用户话语的隐义，也不是优化范围的划分。它的价值仅在于解释组合方式：没有目标纪律，其他能力可能高效地做无用工作；没有连续性，反馈无法积累，体系每次从零开始。若后续测试显示这种分类妨碍触发或导致两个运行型 Skill 被轻视，就应放弃分类，而不是维护理论美感。

## 四、我用什么方法检查全部八个 Skill

我继续采用前六篇形成的 Skill 语义结构：

`Skill = (T, J, B, I, M, A, H, V)`

`T` 是触发谓词，`J` 是它主要承担的工作和状态转移，`B` 是边界与排除，`I` 是不能轻易破坏的不变量，`M` 是判断程序，`A` 是获准采取的行动，`H` 是与其他 Skill 的交接语义，`V` 是验证和演化证据。

这次我再增加一个只用于评审的量：

`ΔU = U(after) - U(before)`

这里的 `U` 不是统一效用分数，而是用户相关状态的变化证据。每个 Skill 必须用自己的对象解释 `after` 比 `before` 好在哪里，并说明没有牺牲哪些关键约束。我检查的不只是 Skill 是否“提到”优势原则，而是原则是否改变了它的实际行为。

具体问题包括：

1. 它解决的是独立问题，还是与相邻 Skill 重复？
2. 它从什么可观察状态开始，到什么状态停止？
3. 它怎样知道信息足够，怎样避免无限分析？
4. 它是否能排除被支配路径，而不只是列出选项？
5. 它怎样保护可行域、选择权和用户主权？
6. 它是否保存能被结果反驳的预测？
7. 它的失败应由自身修正，还是交给另一个 Skill？
8. 哪些文字真正改变行为，哪些只是重复常识或输出格式？

以下不是最终改版，而是基于当前文件的重构命题。

## 五、`first-principles-dialogue`：从庞大的推理大全收缩为认识状态转换器

### 当前真正有价值的本体

这个 Skill 的独特对象是命题与其认识地位。它把一个复杂主张拆成原子事实、公理或原则、假设、目标、设计选择、研究问题和指标代理；为每个子命题指定证据路径；检查逻辑关系和可证伪条件；再重组为一个能够支持或不能支持行动的结论。

它的状态转移可以写成：

`含混或混类的命题 → 分类清楚、证据路径明确、可被反驳、知道会改变什么决定的命题结构`

这是八个 Skill 中最基础的认识能力之一，但“基础”不等于它应接管所有复杂工作。

### 当前问题

它的主文件约一万八千字符，显著大于其他 Skill。触发描述同时覆盖第一性原理、事实清单、研究、商业目标、SMART、营销漏斗、战略、用户行为、指标和数学模型。正文把认识论内核、固定输出协议、商业目标设计、漏斗分析、预算与激励建模放在同一层。

这造成三个劣势。第一，触发过宽：几乎任何商业或战略问题都可能加载它，与 `situational-analysis` 和 `project-framing` 竞争。第二，抽象层混杂：命题分解是一种通用认识操作，漏斗和预算则是特定应用。第三，上下文成本过高：即使用户只问一个简单命题，模型也加载大量不会使用的领域说明。

这里最需要的不是补充优势原则，而是做减法。

### 候选重构

我会把主 Skill 收缩为四个可往返动作：

1. **定题**：确定要判断的命题以及它将影响的决定；
2. **拆分**：区分事实、定义、原则、假设、目标、设计和代理；
3. **检验**：指定证据路径、逻辑关系、反例和最小新增信息；
4. **重组**：给出真值状态、适用条件以及对当前行动的影响。

事实清单、研究待办和研究执行可以保留为条件性输出模式，但不应支配普通对话。商业目标、漏斗、数学与激励模型应移入按需参考资料，或者在真实重复使用证明它们是独立能力后再讨论单独 Skill。它们不能继续使核心本体膨胀。

优势原则对它的具体要求只有三个：所有分解必须服务一个真实判断；研究应在边际信息价值不足时停止；输出必须说明认识变化怎样改变用户可选行动。它不负责综合所有现实后果，那是 `situational-analysis` 的工作。

### 可证伪的优化命题

如果收缩是正确的，那么在简单命题、复杂研究和商业模型三个测试中，精简版应当至少保持事实分类和逻辑质量，同时降低无关展开，并在需要领域方法时正确加载参考资料。若精简后经常遗漏数学关系或商业行动链，说明被移出的内容不是应用材料，而是内核的一部分，需要重新判断。

## 六、`situational-analysis`：从扩大观察范围进化为情境中的策略选择器

### 当前真正有价值的本体

这个 Skill 已经拥有非常接近优势原则的结构。它先理解实际工作，再用证据、逻辑、系统、人性和意义检查判断，沿时间、利益、治理、博弈和哲理扩展观察，比较路径，最后根据行动反馈修正。它明确反对用分析篇幅证明质量，也反对为了全面而无限研究。

它的状态转移是：

`局部成立但现实后果不清的方案 → 在相关语境、证据、主体和变化中仍可承担的下一策略`

### 当前问题

它很擅长发现遗漏，却还没有足够明确地说明何时选择观察、何时行动、何时保持现状，以及何种方案可以直接排除。五层五维虽然被声明不是检查表，但仍可能诱发模型为每个维度生成一段文字。它的“行动与修正”有反馈语言，却没有一个足够紧凑的预期—结果记录，使后续迭代容易重新解释而非校准。

### 候选补充

我不会新增一套优势章节，而会在现有三个环节中增加四个判断：

- 先排除被支配路径；
- 标出不能用平均收益越过的可行性约束；
- 当关键未知存在时，比较获取信息、可逆试验与立即行动；
- 为首选策略写出一项会改变判断的观察和重审条件。

这使它不只是“考虑得更全面”，而是负责从多个可行策略中选择下一政策。它仍不负责证明原子命题，也不负责设计具体架构；必要时调用或交给相邻 Skill。

### 可证伪的优化命题

新版本不应输出更长。它应在有实际取舍的案例中更快删除伪选项，给出更明确的下一行动，并能说出什么结果会推翻该建议；在窄小机械任务中仍应保持沉默。若加入这些判断只增加术语而不改变首选方案、调查范围或停止时机，就应删除。

## 七、`communication-advisor`：从写好沟通进化为改变承诺结构而不损害用户位置

### 当前真正有价值的本体

这个 Skill 的对象不是文本，而是人与人之间的理解、决定、承诺和行动。它区分日常同步、协同决策、边界风险和多方局面；区分事实、解释、未知、建议、决定和承诺；按可控制、可影响和仅可观察划分责任；把不可控结果转换成可控下一步。

它的状态转移是：

`零散事实、模糊责任或不稳定局面 → 相关主体能够理解并承担的决定、承诺、边界与下一动作`

它已经是博弈论在真实协作中的成熟落点，而且没有把所有人预设为敌人。

### 当前问题

它的完成条件偏向“沟通已经被设计或发送”，而持续优势要求进一步观察对方实际回应。当前文件有持续优化，却没有把一次沟通视为策略互动中的一个动作：对方可能同意、拒绝、模糊回应、无权决定或表面支持但不投入资源。若没有回流，这个 Skill 只能优化表达，无法校准局面模型。

此外，它虽然保护用户不替别人承诺，但还可以更明确地区分：用户的最低可接受状态、无协议时的替代行动、哪些让步可以交换、哪些成本不能单方面转移。这里不需要堆入谈判术语，只需让建议不把“达成一致”默认为唯一成功。

### 候选补充

我会增加一个极小的闭环：每次重要对齐都应知道希望改变谁的什么行动、最低可接受结果是什么、若对方没有能力或不愿承诺下一步是什么、什么时候根据真实回应降级或升级分析。

优势原则在这里表现为共同收益与用户位置同时进入模型：寻找正和不等于接受无限责任；自保不等于制造对立；关系成本不能被忽略，但也不能用和气掩盖不可执行的承诺。

### 可证伪的优化命题

在资源请求、标准漂移、跨团队依赖和普通进度同步中，补充后的 Skill 应更准确地区分何时只需一句消息，何时必须改变责任结构。若它让普通沟通普遍变得像谈判，或让用户过度防御，说明优势原则被误用为竞争原则。

## 八、`project-framing`：从澄清项目进化为生成更好的项目可行集

### 当前真正有价值的本体

这个 Skill 处理零到零点一：从模糊意图回到真正要创造的变化，识别用户、当前与目标状态、边界、依赖和假设，探索实质不同的路径，形成暂定项目模型，并选择最有价值的下一步。

它的状态转移是：

`模糊想法或过早方案 → 目标、边界、备选路径、关键未知和下一有效行动足够清楚的项目状态`

### 当前问题

它已经非常接近最小充分设计，但仍有两个边界容易漂移。第一，它会“映射更大系统”和“塑造暂定架构”，可能与 `system-architecture` 重叠。第二，它强调探索可信替代方案，却没有明确区分“生成更多选项”和“扩大可行集”。前者可能只是增加讨论，后者要求新选项在资源、时机和可执行性上真实存在。

### 候选补充

它应拥有选项生成，但只到项目方向层：重新定义问题、改变范围、调整首个切片、采用实验或直接实施。组件职责、状态边界和运行反馈一旦成为主要问题，就交给 `system-architecture`。

我会增加两个判断：候选方向是否真的可行；下一行动究竟是在兑现价值，还是在购买决策信息。这样“先做原型”不再是默认好答案，只有原型能区分关键假设时才成立。

### 可证伪的优化命题

优化后，它应在模糊项目中产生更少但差异更真实的方向，并更早指出哪些决定可延后；在方向已经确定的项目中应更快退出。若它继续为清楚需求制造选项，或者开始设计具体系统接口，边界仍未解决。

## 九、`system-architecture`：从关系设计进化为保持系统可行并可演化的结构能力

### 当前真正有价值的本体

这个 Skill 处理职责、边界、信息、状态、执行、资源、协作、运行和演进之间的关系。它已经明确区分行为指令、模型实测能力和运行环境保证，也允许直接实现、保持现状、删除结构、实验或协商外部支持。

它的状态转移是：

`职责、依赖和反馈关系不清或不适配 → 能够完成工作、承担失败并随证据演化的结构`

### 当前问题

它对“持续演进”有丰富表述，但维护能量和结构熵仍是隐含判断。新增接口、共享状态、人工交接、兼容层和平台能力都会产生持续成本；当前文字强调复杂度相称，却没有要求结构选择显式说明谁长期维护、何时退役、失败怎样被看见。

另一个问题是它可能与 `situational-analysis` 重复比较路径。二者应以对象区分：`situational-analysis` 判断一个行动策略在现实关系中是否成立；`system-architecture` 判断系统部分怎样形成可工作的关系。架构 Skill 可以使用情境判断，但不应重新成为通用决策 Skill。

### 候选补充

每项重要结构选择至少要能回答：它扩大了什么能力或可行域；引入了什么长期维护和协调成本；失败如何被观察；是否存在恢复与替换路径；什么条件触发重审或退役。这里不需要固定文档，只需要判断时不能遗漏。

热力学透镜在这里最有价值的工程化，不是声称组织服从物理熵公式，而是要求任何有序结构说明持续投入。进化透镜则要求接口保留变异空间，不把暂时实现误写成永久本体。

### 可证伪的优化命题

在一个新架构、一个已有系统重构和一个简单局部修改中，优化版应更准确地识别维护债务、观察能力和退出条件，同时仍能对局部修改保持比例。若所有方案都被要求增加监控、恢复和退役文档，它就把风险控制变成了新的结构熵。

## 十、`project-foundation`：从生成合规基础进化为按阶段购买恰当可靠性

### 当前真正有价值的本体

这个 Skill 是八个 Skill 中工程闭环最完整的一个。它有 Start、Check、Advance、Explain 模式，有风险分级、阶段门槛、manifest、事务化生成、确定性验证、测试和明确状态。它不会把“文件看起来正确”当成验证通过。

它的状态转移是：

`一个准备长期开发但尚无可靠基础的新项目 → 风险与阶段相称、能够被本地验证并知道尚缺什么的工程起点`

### 当前问题

它的优势也是风险：确定性生成容易让“基础模块齐全”替代“这个项目当前获得了净优势”。风险资料把八个模块列为所有长期项目的通用模块，随后又要求每个模块通过最小性测试。这两者可能冲突：若模块真正普遍必需，最小性测试只是形式；若某些低风险项目可推迟其中部分模块，通用列表就过强。

它还明确不支持对任意既有仓库进行 retrofit。这是合理边界，但意味着体系对大量真实项目缺少“基础状态审计”路径。不能立即把这个缺口塞进现有 Skill，因为那会扩大本体；应先观察需求频率、风险和与 `system-architecture` 的边界。

### 候选优化

第一步不是增加模块，而是把“可靠性购买”作为判断对象：每个基础能力防止什么具体失败，最晚何时需要，当前增加多少理解和维护成本，若推迟会封死什么选择。已有的最小性测试应真正有权删除或延迟所谓通用模块，而不是只解释它们。

第二步是把 `Ready` 看成阶段性可行，而不是一般质量标签。一个项目可以 Ready to build，但仍不适合真实用户；这种区分当前已有，应继续强化并成为跨 Skill 的状态语言。

第三步只作为实验：收集既有仓库请求，判断需要的是基础审计、架构诊断还是迁移 Skill。没有证据前不扩大 `project-foundation`。

### 可证伪的优化命题

用一个本地一次性工具、一个长期内部应用、一个含真实用户与支付的项目测试。优化后的模块选择应随风险和阶段显著不同，并保持明确的失败防护。若所谓最小性允许关键安全能力被成本理由删除，说明可行性约束被错误当成普通收益权衡。

## 十一、`project-continuity`：从上下文承接进化为跨时间的学习与恢复能力

### 当前真正有价值的本体

这个 Skill 的对象不是某个领域项目，而是用户与我共同推进工作时的连续状态。它区分讨论、执行、插入事项、恢复和复盘，解释新消息是补充、纠正、替代还是取消，保存目标、约束、证据、决定、活跃工作、停点和验证边界，并要求恢复时核实版本与环境变化。

它的状态转移是：

`容易因时间、线程或插入事项而断裂的协作 → 能在保留有效承诺并吸收新证据后继续推进的协作`

这不是其他 Skill 的附属功能。没有它，单次任务可能正确，长期合作却会反复丢失用户校正、复活已经取消的工作，或者把旧判断带入已经变化的环境。

### 当前问题

它目前更擅长保存“我们做到哪里”，还不够擅长保存“我们原来预计什么、后来实际发生什么、模型因此学到了什么”。项目记录若主要由目标、决定和工作项组成，就能恢复执行，却未必能校准判断。

第二个问题是记忆价值没有被明确评估。持续记录越多，维护、检索、过期和误用成本越高。用户这次对“六个”的纠正就是一个微型案例：如果旧草稿只记录“六个核心 Skill”，却不记录这是一项已被用户撤销的解释，未来连续性反而会固化错误。

第三个问题是当前 Skill 将 Subagent 协调写入自身运行规则。这个能力在环境允许时有价值，但它是执行手段，不是连续性本体；未来需要检查相关文字是否因平台规则变化而过时，以及是否值得主文件上下文成本。

### 候选重构

我会把持续状态压缩为四种值得保留的对象：仍有效的目标与约束；具有后续决策价值的证据和用户校正；未完成工作的恢复点；预期—实际—修正组成的学习记录。任何记录都应允许被后续证据覆盖、标记失效或归档。

连续性不负责把每次对话写成日志，也不建立静态用户画像。保存条件应是：未来重新获取的成本或错误使用的风险，是否高于维护这条状态的成本。长期偏好也要带作用范围和最近确认时间。

### 可证伪的优化命题

用项目中断后恢复、用户撤销旧目标、环境版本变化、临时插入事项和一次结果复盘测试。优化后的 Skill 应减少重复询问与错误复活，同时能主动废止失效判断。若记录量增加却恢复更慢，或旧偏好更难纠正，优化失败。

## 十二、`goal-discipline`：从防止无用工作进化为优势贡献约束

### 当前真正有价值的本体

这个 Skill 要求每个非平凡步骤至少获取能改变决定的信息、改变请求对象或减少成功所需的重要不确定性与风险，并要求在正确状态停止。它同时保护用户明确要求的过程、深度和交付物，不用“简化”取消用户意图。

它的状态转移是：

`可能被流程、工具和可见工作量牵引的行动集合 → 只保留服务实际结果并在正确完成状态停止的行动集合`

它不是主控，因为它不决定事实真假、不替用户定义目标，也不选择专业方案。它是一个行动过滤器。

### 当前问题

现有三类贡献条件已经接近优势原则，但“改变请求对象”仍可能过宽：生成更多文档、代码或计划都可以声称改变了对象，却未必改善用户状态。它还没有显式要求比较一个行动与更低成本替代行动，也没有区分即时交付贡献、学习贡献、选择权贡献和保持可行的必要成本。

另一个风险是全局启用。约束写得越复杂，每个任务承受的判断成本越高，最终可能违反它自己的最小性原则。因此优化必须是压缩，而不是把第一章公式搬进来。

### 候选补充

最小改动可以只替换一个判断：非平凡步骤必须预期改善用户相关状态、获得会改变后续行动的信息，或守住完成目标所需的关键可行性；若存在更低成本、同等效果的授权路径，优先后者。交付物只有在被使用后产生预期状态变化时才构成最终价值，但用户明确请求交付物本身时，完成该交付仍然是当前目标的一部分。

它还需要一个反加法问题：这项结构如果不建立，会发生什么具体失败？如果答案只是“体系看起来不完整”，就不应建立。

### 可证伪的优化命题

用深度研究、明确机械修改、用户指定长文、复杂工程实现和无关文档建议测试。优化版应删除无贡献步骤，却不以最小化为借口削减用户明确要求的深度。若它频繁否决探索、创作或必要的中间产物，说明贡献定义过窄。

这两个运行型能力共同使优势原则跨任务存在，却仍不形成中央大脑：一个让有效状态与反馈能够跨时间延续，一个过滤与真实结果无关的行动。它们与其他六个一样属于完整优化对象。

## 十三、八个 Skill 之间需要什么接口，而不需要什么编排器

没有主控，不等于 Skill 之间没有关系。关系可以由对象和交接条件表达，而不由中央流程表达。

我得到八种状态对象：

- 命题状态：什么是真的、假设是什么、证据缺口在哪里；
- 决策状态：在现实关系和不确定性中，下一策略是什么；
- 承诺状态：谁理解、决定、承担并采取什么行动；
- 项目状态：要创造什么变化、边界是什么、下一有效行动是什么；
- 结构状态：职责、信息、资源和反馈怎样连接；
- 基础状态：项目在当前阶段是否具备可验证的工程起点。
- 连续状态：哪些目标、证据、决定、校正和恢复点仍然有效；
- 贡献状态：当前行动集合中哪些真正服务结果，哪些应被删除或停止。

它们形成的是条件性交接，不是固定流水线：

- 当决策依赖一个尚未成立的关键命题时，进入 `first-principles-dialogue`；
- 当命题已足够清楚但现实取舍仍不明确时，进入 `situational-analysis`；
- 当决定需要其他人形成理解、授权或承诺时，进入 `communication-advisor`；
- 当用户的项目对象、方向或首个切片仍不清楚时，进入 `project-framing`；
- 当问题已经是职责、依赖、状态和运行关系时，进入 `system-architecture`；
- 当新长期软件项目需要生成和验证本地工程基础时，进入 `project-foundation`。
- 当工作需要跨讨论、执行、中断和恢复保持有效状态时，进入 `project-continuity`；
- 在所有实质工作中，由 `goal-discipline` 静默过滤无贡献步骤，但不接管专业判断。

多个对象可以同时存在，但不意味着所有 Skill 都应加载。主 Agent 根据当前决定性问题使用最少充分能力。交接的最小语义不是一份统一表格，而是四项：已经知道什么；当前需要改变哪个对象；哪些约束必须保留；什么结果算完成。

如果两个 Skill 同时声称拥有同一个状态转移，就必须重新划界。例如 `project-framing` 可以提出暂定系统边界，但当结构关系本身成为主要判断时应停止；`situational-analysis` 可以考虑多方回应，但当用户需要生成具体对外承诺时应交给 `communication-advisor`；`first-principles-dialogue` 可以导出行动含义，但不应替代整个情境权衡。

## 十四、我如何把“持续最优”变成可运行而不假装全知

一次性最优选择可以写成 `argmax`，持续最优更接近策略：不同状态下采取不同动作，并根据新观察更新。Skill 体系的运行单元因此不应只是回答，而应是一个最小闭环：

`观察当前状态 → 选择足够合适的能力 → 产生状态变化 → 观察结果 → 更新相关判断`

这里最困难的是结果往往晚于回答出现，而且可能发生在系统外。工程上不能假装自动拥有反馈。可行做法是分层：

1. 在单次任务内，验证能立即验证的事实、文件、测试和结构；
2. 对外部行为，明确预期回应与下一观察点；
3. 在持续项目中，由 continuity 在用户回来时承接结果；
4. 对高价值重复模式，建立可复跑案例，而不是依赖记忆中的成功印象；
5. 只有重复证据显示缺口稳定存在，才修改 Skill。

因此“持续获得最优解”不是每轮都重新计算一个巨大的总模型，而是持续缩小模型与现实之间的差异。最优性的工程近似包括：不保留明显劣势路径，不越过硬约束，不为无价值信息付费，不过早封死未来，选择能够产生反馈的行动，并在反馈出现后真正修改判断。

## 十五、用八个情境测试候选体系

### 情境一：用户问一个看似深刻但定义混乱的商业命题

若直接使用 `situational-analysis`，它可能讨论很多现实后果，却建立在混类概念上。决定性问题是命题状态，因此先由 `first-principles-dialogue` 区分目标、事实、代理和假设。若拆分后发现没有行动差异，工作可以停止，不必升级成战略项目。优势来自减少虚假问题，而不是提供更多建议。

### 情境二：用户已有三个可行方案，但担心遗漏长期代价

此时不需要重新定义项目，也不需要原子化所有句子。`situational-analysis` 比较真实路径，排除被支配选项，识别可行性约束和信息价值，给出下一策略与重审条件。优势来自更好的政策选择。

### 情境三：用户知道应该做什么，但需要领导确认资源

项目和决定已经清楚。`communication-advisor` 识别决定者、用户可控制部分、所需资源与可交换变量，把请求压缩成对方能够作出的决定，并准备模糊回应后的下一步。优势来自改变承诺结构，而不是再次论证项目价值。

### 情境四：用户有一个大产品想法，却不知道第一版是什么

`project-framing` 识别想创造的变化，生成少数真实方向，删除被资源和时机支配的方案，用最小实验购买关键信息。若首个切片已清楚，它停止，不设计全部架构。优势来自扩大并收敛项目可行集。

### 情境五：一个 AI 工作流经常在交接处丢状态

这不是一般项目模糊，也不仅是情境决策。`system-architecture` 检查状态所有权、信息来源、交接协议、运行环境保证、观察和恢复路径；必要时用实验比较结构。优势来自改变关系和反馈，而不是新增提示词。

### 情境六：用户准备开始一个长期内部应用

`project-foundation` 根据真实用户、数据、外部写入、运行形态和维护期选择阶段与模块，生成并验证基础。若只是一次性本地脚本，它应判断该 Skill 不适用。优势来自按阶段购买可靠性，而不是让所有项目看起来像生产系统。

### 情境七：用户中途纠正了体系范围，两天后要求继续

`project-continuity` 应保留新的有效范围，明确旧的“只优化六个”解释已经失效，并从正确停点恢复；它不应复述整段历史，也不应把用户曾经的口误当作稳定偏好。优势来自避免错误状态跨时间繁殖。

### 情境八：研究过程中不断出现值得继续读的资料

`goal-discipline` 不应因为“还可以更全面”而让研究无限扩张，也不应因为已有两万字就机械停止。它检查新增资料是否会改变 Skill 改版、证据强度或风险判断；若不会，就停止。优势来自把注意力留给真正会改变结果的工作。

八个情境显示，优势原则并没有让八个 Skill 趋同。相反，它要求每个 Skill 更忠于自己的对象，因为只有清楚的本体才能知道状态究竟改善了什么。

## 十六、接下来的交付物不应是一套新体系说明，而应是八个可验证的改版

如果我现在继续写一份宏大的“优势 Skill 体系规范”，我会再次把文字完成当成系统完成。合理交付物应从高证据、低耦合改动开始。

### 第一批：减法和边界

最优先的是 `first-principles-dialogue`。它的本体明确，但主文件混入多个应用领域，触发过宽、上下文成本最高。交付应是一个精简核心加按需参考资料的重构，并用原有事实清单、研究、商业目标和漏斗案例验证没有丢失能力。

同时为全部八个 Skill 写出一句状态转移和相邻边界，但不要求统一输出。这可以直接暴露重复：哪个 Skill 拥有问题，哪个只提供局部方法。

### 第二批：补闭环

给 `situational-analysis` 增加支配、可行性、信息价值和重审条件；给 `communication-advisor` 增加真实回应回流与最低可接受状态；给 `system-architecture` 增加维护、可观察、恢复与退役判断。每项都应先用案例比较前后行为，只有改变实际选择才保留。

### 第三批：改善项目状态生成

给 `project-framing` 明确项目方向层与结构层的退出边界，并检验原型是否真的购买信息。重新检验 `project-foundation` 的通用模块和最小性测试是否冲突，先修正选择逻辑，再考虑扩大适用范围。

### 第四批：重构两种运行能力

重构 `project-continuity` 的有效状态、失效和预期—结果—修正记录；压缩增强 `goal-discipline` 的状态贡献、低成本替代和反加法约束。两者都需要独立案例和版本验证，而不是顺手附加两条规则。

由于两个系列是独立仓库，实施也应保持独立的复制、测试和提交边界。概念上可以共同设计，修改时不能用一个跨仓库大提交制造伪统一。先改 Cognitive Skills，验证三种认识与协作能力；再把得到的评价方式用于 Project Craft，会比同时重写八个 Skill 更可恢复。

## 十七、我需要怎样评价这些改版

格式验证只能证明 Skill 可加载，不能证明它帮助用户获得优势。评价必须围绕前后行为差异。

每个 Skill 至少准备三类案例：典型案例、邻接边界案例、反例或低强度案例。分别检查它是否完成独特状态转移，是否知道何时交接，是否知道何时不展开。对具有随机性的模型行为，应重复运行，并保留输入、版本、环境和评价依据。

共同评价问题可以保持很少：

1. 它是否识别了真正需要改变的对象？
2. 它是否删除了明显被支配的工作或方案？
3. 它是否保护了关键可行性约束和用户授权？
4. 它是否在正确时机选择研究、实验、行动或停止？
5. 它是否给出可观察的状态变化，而不只是更完整文字？
6. 它是否留下了能被真实结果推翻或修正的判断？
7. 相比无 Skill 或旧版本，它增加的上下文与步骤是否值得？

这些问题不是输出模板，而是离线评审。若一个改版提高某项质量却显著增加普通请求的延迟、篇幅或误触发，它未必形成净优势。

## 十八、哪些东西现在不应该做

我不应创建 `advantage-system` 或 `optimal-state` Skill。没有独立对象，也没有现有能力无法承担的稳定状态转移。

我不应要求所有 Skill 输出统一决策记录。记录只在需要跨时间恢复、比较或审计时有价值。

我不应把七条分布式原则复制进八个主文件。重复会增加上下文和维护分歧。原则应转化为各 Skill 自己的少数行为规则和共同评价案例。

我不应同时重写两个仓库。这样无法判断结果来自哪个改动，也违反独立发布边界。

我不应把“六个对象型加两个运行型”立即固化成正式架构。它目前只是由本体审计得到的候选解释，而且用户已经证明我容易把偶然措辞过度理论化。它必须由路由冲突、真实使用和改版实验验证。

我不应承诺体系能在任何情境中发现全局最优。它能做的是在任何进入的情境中，更可靠地识别问题类型、约束、可行行动和反馈，使找到更优状态的概率与能力持续提高。

## 十九、第一次快速改版应具体交付什么

这一章仍是研究文字，但它已经足以约束下一次实施。所谓“迅速补充或者重构”不能理解为同时往八个文件追加原则。速度来自缩小第一次改版的因果范围，让每个变化都能被比较和撤销。

### Cognitive Skills 的第一次改版

`first-principles-dialogue` 的主要动作应是重构而不是补充。保留命题、认识分类、证据路径、证伪、重组和行动含义这一核心；把商业目标、漏斗、数学模型、激励与预算等应用方法迁入按需参考文件。前置描述也应缩小，避免用户只提到“策略”或“指标”就自动加载一万多字符。现有三种固定输出模式需要保留兼容测试，不能因追求简洁而破坏用户明确依赖的格式。

它的第一版完成证据不是主文件变短，而是四组旧能力对照：普通第一性原理对话、事实清单、研究执行、商业或漏斗建模。新版应在前三者保持或改善认识质量，并在第四类正确加载应用参考。若领域任务质量明显下降，就回滚迁移边界，而不是用“核心更纯”辩护。

`situational-analysis` 只做最小补充：在比较路径时先识别被支配方案和不可平均的约束；在信息不足时比较调查、试验和行动；为首选策略保留一个改变判断的观察。随后扩展现有验证案例，不新增输出模板。检验重点是首选行动和停止时机是否变化，而不是回答中是否出现“可行域”或“选择权”。

`communication-advisor` 增加回应闭环：重要沟通要明确希望改变的行动、最低可接受结果、对方无权或拒绝时的下一步，以及什么真实回应会使分析降级或升级。普通消息改写必须作为反例，确保新规则不会把所有交流变成谈判。多方参考资料可以承载复杂分支，主文件只保留决定行为的最小规则。

这三个修改位于同一仓库，但仍应分成可识别的变更和测试。最值得先做的是 `first-principles-dialogue`，因为它的上下文成本和本体混杂最明显；后两个可以作为较小补丁分别验证。不能用一次“大版本升级”掩盖哪个改动有效。

### Project Craft 的第一次改版

`project-framing` 只需补强两个退出判断：候选方向必须是资源和时机上真实可行的方向；一旦主要未知从“做什么项目”变成“各部分怎样连接”，就把结构问题交给 `system-architecture`。原型必须说明它将区分哪个关键假设，否则不能仅因可逆就成为默认下一步。

`system-architecture` 增加结构生命周期判断：每项重要新增关系由谁维护，失败如何观察，怎样恢复或替换，什么条件要求退役。它不能把这些问题变成强制文档，也不能对普通局部改动自动展开完整分析。至少需要新系统、已有系统演进、AI 指令与运行保证混淆、简单修改四类案例。

`project-foundation` 的第一次工作是检验，不急着改生成器。用不同风险与生命周期项目运行模块选择，检查“所有长期项目的通用模块”是否与“每个模块都能被最小性测试删除”存在真实冲突。若冲突成立，再修改 manifest 选择逻辑、文档和测试；若只是措辞问题，只修正文义。现有确定性测试和事务生成不能被理论重构破坏。

`project-continuity` 增加状态失效与学习记录：用户纠正、目标撤销、版本变化和实际结果出现时，旧判断怎样被标记、哪些后续工作受影响、何时不值得记录。它应优先复用已有项目记录，不创建新的中央记忆文件。恢复测试必须同时检查“少问重复问题”和“没有错误沿用旧状态”。

`goal-discipline` 的改动应最小，因为它全局启用。把贡献条件从“改变对象”收紧为改善用户相关状态、获得会改变行动的信息或守住关键可行性；再增加低成本同效路径与反加法判断。通过长文、创作、研究和必要中间产物案例确保它没有把所有价值压缩成短期可量化结果。

Project Craft 是独立仓库，修改时必须在它自己的 Git 边界内完成测试、提交和发布。第二章保存在 Cognitive Skills 只因为研究材料当前位于该仓库，不代表 Cognitive 仓库取得另一个系列的实现所有权。

### 第一次改版的停止条件

每个 Skill 达到以下状态就应停止当前版本：独特状态转移更清楚；与相邻 Skill 的误触发或重复减少；至少一项真实行为因改动改善；低强度反例没有显著变差；新增文字和维护成本可解释。没有证据支持的第二轮设想保留在研究记录中，不顺手实现。

如果某个 Skill 经过测试无需修改，这也是有效结果。体系优化不等于八个文件都必须产生 diff。第一轮真正的交付物应是少数经过行为对照的改版、明确保持不变的部分、失败或无差异的实验，以及下一次只有在新证据出现时才启动的候选问题。

## 二十、结论如何从这次检查中长出来

我最初以为用户的问题会把我带向一个更高的总原则：既然我的工作是帮助用户获得优势，就需要一个统一优势系统来规范所有 Skill。实际检查给出了相反结论。

越认真接受“持续生成更优状态”这个目标，我越不能让所有能力服从同一种表面流程。不同现实对象具有不同结构：命题需要证据和逻辑，决定需要情境与策略，人际协作需要承诺与回应，项目需要边界与方向，系统需要职责与反馈，工程基础需要风险和验证，持续合作需要可修正状态，行动纪律需要贡献与停止。把它们统一，会丢失产生正确判断所需的差异。

真正统一它们的是责任：每个 Skill 都要对自己声称改善的状态负责；要说明凭什么更好；要避免被更简单路径支配；要守住自己能够看见的可行性约束；要在信息价值不足时停止；要允许结果回来推翻它。这个统一存在于评价和演化中，而不是存在于中央控制中。

于是，“我的最优解是不是持续帮助用户获得优势”得到了更精确的回答：我的最优策略是帮助用户持续进入更优的可达状态，并提高我们共同识别、创造和进入这些状态的能力。我的直接产物可能是事实结构、决定、消息、项目边界、架构、工程基础、可恢复项目状态或对无用工作的停止；这些都只是载体。最终要观察的是用户的现实状态和未来可行集是否改善。

这也决定了接下来 Skill 体系的候选形态：八个各自拥有状态对象的能力，其中六个主要处理对象特定问题，两个主要处理运行状态；通过条件性交接协作，不通过总控编排；先收缩最臃肿的能力，再补真实反馈闭环；用案例和结果决定是否保留改动；只有稳定缺口证明存在新的独立本体时，才创建新 Skill。

我没有因为发现一个好原则而增加一层系统。相反，这个原则迫使我删除不必要的层，要求每个已有能力更准确地完成自己的工作。这可能是这一章最重要的结论：优势原则最先优化的不是用户，而是我自身采取行动的纪律。
