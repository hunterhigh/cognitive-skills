# 控制：我怎样把 Skill 看成不完备模型驱动的调节器

## 控制并不等于命令

当我把“控制”带入 AI Skill 设计时，最危险的直觉是：只要把指令写得足够严格，输出就会服从；只要增加检查项，我就能控制复杂任务；只要指定目标，系统就会朝目标收敛。这种直觉把控制当作单向命令，把语言要求当作物理约束，也忽略了模型、工具、用户和环境都具有我不能完全预测的状态。

控制论对我的真正挑战是：如果一个调节器看不到关键状态，没有足够的行动选择，反馈到达太迟，目标本身又含糊或互相冲突，那么再强烈的命令也不会产生可靠控制。控制不是“我要求什么”，而是系统在扰动下能否让某些重要变量保持在可接受范围，或者从当前状态到达目标区域。它是一种闭环能力。

我关心的情境很具体。`goal-discipline` 要求非平凡步骤服务用户真实结果；`project-continuity` 要求项目可恢复；`project-foundation` 要求生成后进行真实验证；`situational-analysis` 要求随证据和情境修正判断。这些 Skill 都隐含调节问题：有参考状态，有现实状态，有偏差，有观测，有行动，也有停止或重审条件。如果不把这些元素说清楚，Skill 就容易退化为愿望清单。

## 最小控制结构

我把最小闭环写成：

`plant: x(t+1) = f(x(t), u(t), d(t))`

`observation: y(t) = h(x(t)) + n(t)`

`error: e(t) = r(t) - y(t)`

`controller: u(t) = π(y(0:t), r, m, c)`

被调节对象 `plant` 可以是代码库、项目协作过程、一个决策或用户与 AI 的工作状态。`x` 是不能完全直接看见的真实状态，`u` 是我能采取的行动，`d` 是扰动，`y` 是经过测量得到的观察，`n` 是噪声，`r` 是参考目标，`π` 是依据历史观察、内部模型 `m` 和约束 `c` 选择行动的政策。

这个结构让我立刻发现几种常见混淆。目标不是指标；`r` 是想维持或到达的真实条件，而 `y` 往往只是代理观察。行动不是结果；写文件、提问、运行测试是 `u`，不是完成。反馈不是任何返回信息；只有能改变后续判断或行动的信息才进入闭环。检查不是控制；如果检查发现偏差却没有授权或能力修正，只有监测。自动化也不是闭环的充分条件；一个按时重复执行但不读取结果的任务是开环程序。

在 Skill 语境中，“用户满意”太宽，不能直接成为可操作参考。不同 Skill 需要更具体的受控变量。例如 `project-framing` 可以把“方向足以支持下一有用动作”作为目标区域，而不是要求所有未知归零；`project-foundation` 可以把结构验证、风险模块和运行工具结果作为可观察条件；`project-continuity` 可以把“另一回合能够从已核实状态恢复工作”作为可测试结果；`first-principles-dialogue` 可以把“关键复杂命题的原子依赖、证据状态和证伪条件被明确”作为判断完成度。

目标常常不是一个点，而是可接受集合 `R`。过度精确会让调节器追逐虚构精度。项目方向可能允许多个可行解；沟通不可能保证对方内心状态，只能提高共同理解和明确承诺的概率；AI 输出存在波动，验证需要分布而非一次样例。于是控制目标应同时包括边界：哪些变量必须保持，哪些可以变化，允许多大误差，何时宁可停止而不是继续纠偏。

## 可观测性：我不能调节看不见的东西

如果两个不同内部状态产生相同观察，我就无法仅凭该观察判断该采取什么动作。这是可观测性问题。用户说“可以”可能表示真正同意、暂时敷衍、只同意其中一部分，或者不想继续讨论；一次测试通过可能表示实现正确，也可能表示测试没有覆盖失败路径；项目文档存在不表示信息仍然有效。

因此 Skill 首先要判断需要什么证据，而不是立即行动。`first-principles-dialogue` 的证据分类提供观测语义：直接事实、定义、公理、假设、目标、设计选择、研究问题和代理指标不能混成同一信号。`situational-analysis` 则补充观测范围：一个技术方案本地成立，不代表在人力、时间、治理或利益关系上成立。`communication-advisor` 必须承认人的意图是部分可观察的，不能把措辞分析升级为动机事实。

观测也有成本。为了完全了解项目，我可以读取所有文件、历史和外部材料，但这会消耗时间与注意力，甚至制造新的隐私风险。控制器不应追求全知，而要寻找足以区分当前决策的最小观测。问题是“哪一条新增证据会改变动作”，而不是“还能收集什么”。这与 goal-discipline 形成直接联系：证据收集只有在可能改变决定、降低重大风险或验证完成时才服务目标。

我还必须处理观测延迟和信号质量。一些信号即时但低价值，如输出字数、文件数、清单完成率；另一些信号迟到但高价值，如真实使用中的恢复成功、维护成本、跨情境稳定性。只用即时信号会把系统调向代理指标。工程上需要“信号组合”：近端过程证据用于快速纠偏，终端结果证据用于验证方向，长期维护证据用于决定是否保留结构。

## 可控性与必要多样性

控制器必须拥有足够的行动多样性来应对环境多样性。Ashby 的必要多样性法则经常被简化成“只有多样性才能吸收多样性”。我对它的工程理解是：如果可能出现的相关扰动类别超过调节器能够区分和响应的类别，某些结果就无法被稳定限制。增加规则数量不是唯一办法；我也可以减少扰动、改变系统结构、隔离高风险路径、增加工具能力、请求人类决定，或者放宽目标集合。

在两个 Skill 系列中，这意味着不能指望一个通用提示词处理所有项目状态。一个只会“给建议”的 Skill，无法在用户要求实际修改时完成闭环；一个没有读取仓库能力的架构判断，只能停留在假设；一个没有外部授权的助手不能真正协调第三方承诺。正确行为不是假装控制，而是明确能力边界，改变目标、获取授权或交接。

必要多样性也不等于每个 Skill 都要覆盖所有异常。系统可以通过组合获得多样性：foundation 用严格验证处理新项目基础，architecture 处理关系重组，situational-analysis 处理高影响取舍，work-alignment 处理外部人类响应。关键是路由器能识别扰动类别，且交接不会丢失状态。若所有 Skill 都复制所有响应，成本上升，冲突增多，反而降低有效多样性。

我可以把 Skill 的响应能力粗略看成集合 `U_S(c)`：在情境 `c` 下，它被授权且有能力采取的动作。环境需要处理的扰动集合为 `D(c)`，目标允许的结果集合为 `R(c)`。工程问题是映射 `π: observations(D) -> U_S` 是否足以把结果保持在 `R`。当答案是否定时，解决方式可能是增强观察、扩大动作集合、降低环境复杂度、重新划分边界，或把判断交给别的控制层。

## 内部模型与“好调节器”

Conant 与 Ashby 的 Good Regulator 定理经常被传播成“每个好的调节器都必须是系统的模型”。原论文结论有明确数学条件，不能把它当成所有管理情境的无条件格言。但核心提醒对我重要：有效调节需要保留与被调节系统相关的结构差异。一个把所有失败都归为“用户没说清楚”的控制器没有足够模型；一个把项目只看成代码组件，会忽略人、权限和维护；一个把 Skill 的文本当成行为本身，会忽略模型和运行环境。

我的内部模型不需要复制整个现实，它必须对当前调节任务充分。模型的价值由它支持的干预决定。对于 `project-framing`，我需要知道目标、当前状态、关键约束、候选方向和重要未知；不必提前建立完整部署拓扑。对于 foundation，我需要更严格的风险、运行环境、数据和阶段模型，因为生成基础具有长期影响。对于 work-alignment，我需要多方职责、利益和承诺状态，但不应臆测心理诊断。

因此 `M`——Skill 的判断程序——应显式表明它依赖的系统模型和模型分辨率。若模型假设失效，控制行动就应降级或暂停。Skill 的“专业感”不来自永远给出动作，而来自知道何时内部模型不足以支持动作。

## 目标、控制者和价值冲突

控制论的形式表达容易隐藏政治问题：谁设定 `r`，谁承受控制成本，谁能改变规则，谁的偏差被视为错误。对 AI Skill，这不是附加伦理章节，而是控制结构本身。用户、组织、平台、模型供应者、项目维护者和受影响第三方可能拥有不同目标。把其中一个目标写成系统唯一参考，会把价值选择伪装成技术事实。

`goal-discipline` 要守护的是用户实际请求，但仍受更高层安全、权限和现实约束。`communication-advisor` 不能以“达成一致”为唯一目标，因为表面一致可能通过压制异议取得；更好的受控变量是理解、决定、承诺和可执行行动的清晰度，同时保留不同意的合法空间。`system-architecture` 不能只优化吞吐量，也要暴露维护责任和失败承担者。

控制对象有自主性时，干预会改变其策略。人会适应指标，团队会绕开繁琐流程，用户会学会如何触发模型，Skill 作者会针对评测样例优化。这使闭环与博弈、进化相连：反馈不只是被动测量，还会改变环境。一个指标一旦成为目标，信号结构可能失真。控制设计因此需要反操纵观察、多个互补指标、人工复核以及对意外行为的开放记录。

## 我怎样重新理解八个 Skill

`first-principles-dialogue` 是认识控制器的一部分。它减小“判断状态”与“证据所支持状态”之间的偏差，通过分解和证伪提高观测分辨率。但它不应把所有命题都压成静态原子；关系和时间本身也是事实结构。它的闭环不在于完成一张表，而在于新证据能真正改变复合命题判断。

`situational-analysis` 是模型预测控制的近似：它在行动前考虑多层后果和未来情境，选择当前可行且可修正的动作，并设置重审条件。它不能保证预测正确，所以必须保留不确定性和低成本反馈路径。越不可逆，越需要更强模型与证据；越可逆，越可用小实验代替长分析。

`communication-advisor` 是跨主体协调控制器，但不能直接控制他人。它能控制的是信息表达、请求、承诺确认、升级与后续动作；对方响应是环境输入。其成功不是让别人服从，而是让协作状态从含糊变得可判断。

`project-framing` 调节的是方向不确定性。它把模糊愿望转成足以行动的目标区域、边界和下一步。过度控制表现为在高不确定阶段规定完整规格；控制不足表现为只复述愿望，没有形成可检验方向。

`system-architecture` 调节的是结构与工作之间的适配。它使用实现、实验和运行反馈改变职责、接口、信息流和资源安排。它尤其要区分指令性要求与环境强制保证：写在 Skill 中的“必须”不能替代权限、事务、类型、测试或运行隔离。

`project-foundation` 是最接近显式状态机的 Skill。Start、Check、Advance、Explain 是模式；manifest 是内部模型的一部分；validate、generate、verify、status 是不同闭环动作；Ready/Not ready 是经过证据判断的状态。它的事务性和“不把看似合理文件当成功”是成熟控制思想。

`project-continuity` 调节项目的可恢复性。它通过选择性记录、重读和状态更新抵抗上下文断裂。其测量不是文档存在，而是恢复者能否识别当前目标、有效事实、活跃工作、停点和恢复条件。记录过多会增加观测噪声和维护负担。

`goal-discipline` 是上层参考与停止调节器。它不断检查当前步骤是否仍服务真实结果，并在完成时停止。它要避免积分饱和式失败：因为已经投入很多步骤而继续扩大工作，或因为目标叙述太宽而永远不能完成。

## 工程化：从说明文档到可验证闭环

我希望每个 Skill 的工程说明至少能回答八个控制问题：受控对象是什么；目标区域是什么；能观察哪些信号；哪些关键状态不可直接观察；能采取哪些动作；存在哪些扰动与延迟；何时停止、交接或升级；用什么终端证据验证结果。它们可以映射回 `T/J/B/I/M/A/H/V`，但控制论让这些字段具有动态含义。

我会把评测从“是否遵循步骤”改成闭环场景。一个完整案例至少包含初始状态、扰动、部分错误信息、工具失败或用户纠正，以及预期的状态恢复。评价不仅看首答，还看收到反证后是否修正、是否保留用户决定、是否在能力不足时正确交接。静态黄金答案无法充分测量调节能力。

我还需要建立失效分类：传感失败——没看到相关信息；状态估计失败——看到信号却误判内部状态；模型失败——因果结构错误；执行失败——动作没有生效；权限失败——动作越界；目标失败——参考本身矛盾或不正当；延迟失败——反馈太晚；接口失败——交接丢失；停止失败——完成后继续扩张。这样的分类比“回答不好”更能指导 Skill 修改。

版本演化也应是闭环。修改前写明目标失败模式和预期信号；建立基线案例；修改一个主要机制；比较成功、误触发、成本和新失败；决定保留、回退或进一步实验。若同时重写触发、流程、输出和工具策略，即使结果改变，我也无法知道哪个机制有效。

在系列层，我倾向于设置分层控制，而非中央总控。局部 Skill 处理快速、可逆的任务偏差；项目系列处理跨回合状态和结构；用户保留目标与重大权衡的决定权；平台和权限层提供硬约束。上层只在局部无法吸收扰动、目标冲突或影响扩大时介入。这样可以减少一个总 Skill 的模型负荷，也更符合不同时间尺度。

## 我必须拒绝的控制幻觉

第一，指令幻觉。提示中写“永远”“必须”不能保证模型在所有上下文中遵守，更不能保证外部系统状态。真正的硬约束应尽量由运行环境、权限、事务、验证器和审批边界承担。

第二，指标幻觉。格式合规、测试数、覆盖率、字数和任务完成标记都是观测，不是目标本身。任何代理都可能在成为目标后被优化到失真。

第三，预测幻觉。复杂人类项目不可完全建模。闭环的优势不是消除未知，而是用可恢复行动持续校正。高影响不可逆动作仍需更强前置判断。

第四，全局控制幻觉。没有单一观察者拥有全部信息和合法权威。分布式知识、局部自治和协商不是系统缺陷，而是现实条件。

第五，稳定等于不变。控制系统的稳定是扰动后仍能保持或恢复关键性质，不是冻结所有结构。Skill 若不能因环境和证据变化而更新，只是僵化。

## 我怎样为每个 Skill 写反馈契约

为了避免闭环只停留在比喻，我为重要工作设计一个内部 `FeedbackContract`：`desired_state` 是希望存在的现实条件；`controlled_variable` 是我试图影响的变量；`observable_signal` 与 `measurement_source` 说明怎样知道变化；`observation_delay` 与 `evaluation_window` 说明何时评价；`allowed_actions` 与 `authority_boundary` 限制行动；`tolerance` 说明可接受区域；`stop_or_escalation_condition` 说明何时停止或交接；`model_revision_condition` 说明什么反证要求重建判断。它不要求用户填表，只是我设计 Skill 和评测时不能遗漏的语义。

对 `first-principles-dialogue`，desired state 不是“输出五个标题”，而是关键命题依赖和真值状态足够清楚；信号是可复核原子命题、证据路线和证伪条件；模型修订条件是新证据推翻前提或发现关系不能被独立原子表示。对 `project-framing`，目标是方向足以支持下一有效动作；信号是结果、边界、主要未知和下一步具有一致性；停止不是完整需求，而是继续 framing 的信息收益低于行动学习。

对 `communication-advisor`，我无法控制他人接受，只能控制消息、请求、事实准确、承诺确认和跟进；反馈是对方的明确回应或实际行动，延迟由协作节奏决定。若没有返回通道，一封完美消息仍是开环。对 `system-architecture`，目标不是架构文档，而是职责、信息、资源和执行关系足以完成工作；真实反馈来自实现、运行、故障和维护。对 `project-continuity`，目标是可恢复；评价应让另一个回合根据记录继续，而不是统计文档长度。

这些契约还揭示控制层次。用户决定目标和重大取舍；Skill 选择局部判断与行动；工具和 runtime 执行并提供硬约束；外部人员有独立目标，只能协调。一个层级不能静默重写上层参考，也不能承诺下层没有保证的性质。

## 失败诊断矩阵

我不再从“结果不好”直接跳到“加一条 prompt”。目标定义失败意味着参考状态含糊或冲突；边界失败意味着遗漏重要对象或把成本推出系统；传感失败是没有获取关键事实；可观测性失败是已有信号无法区分状态；状态估计失败是从信号推错；模型失败是因果结构错误；政策失败是判断模型尚可但行动选择不当；可控性失败是缺少权限或工具；执行失败是动作没有生效；延迟失败是过早评价；环境变化是原模型条件失效；博弈失败是自主主体作出不同响应；指标腐化是信号因被优化而不再代表目标。

同一个表面症状可以属于不同类型。项目没有推进，可能目标不一致、负责人无权限、消息未送达、依赖延迟、对方策略拒绝或完成指标错误。如果我只加强沟通，就会在执行器坏掉时提高控制信号频率，造成振荡和疲劳。

这套分类也改变回归测试。每次 Skill 修改必须声明修复哪类失败。如果修复可观测性，就应加入两个产生相同表面信号但内部状态不同的案例；如果修复权限，应测试只读、建议和实际执行边界；如果修复延迟，应测试在反馈未到前能否等待；如果修复模型，应测试反证后是否重建而非局部补丁。

## 稳定性、增益与振荡的具体推演

我把“高增益”理解为对小偏差做过大调整。用户说“这部分有点长”，我若把整个方法论压缩成一句话，就是高增益；一次测试失败就重写全部 Skill，也是高增益。低增益则可能对严重失败只做表面措辞修补。合适增益取决于证据强度、失败严重度和变化可逆性。

振荡常见于目标与反馈解释不稳定：用户要求更自主，我减少提问；随后一次错误使我增加确认；确认太多又被要求自主，于是在两个极端来回。解决不是寻找永久中点，而是区分风险情境：低风险可自主，高风险或不可逆动作需确认；把控制政策变成基于状态的响应，而非全局风格。

积分式累积也有类比风险。长期未解决的小偏差可能让规则不断累加，直到 Skill 过重；一次历史事故留下永久步骤，即使环境已变。维护时需要 anti-windup：检查旧规则是否仍有作用，目标达到后停止累积，环境改变时重新估计，而不是让历史误差无限进入当前政策。

采样频率同样不能越快越好。项目状态尚未改变时频繁检查只产生噪声；反馈过慢又会让错误扩散。continuity 和 automation 应按变化速度、影响和响应成本设定节奏。用户没有要求周期状态时，系统也不应为展示活跃而不断通知。

## 闭环仍不能取代判断

反馈能修正，但不可逆高损失动作不能依赖失败后学习。敏感数据外泄、破坏生产、发送伤害性消息不适合“先做再闭环”。这时应使用前馈：基于已知风险设置权限、隔离、预演、静态验证和人类审批。反馈与前馈互补。

目标本身也会变化。经典 setpoint 容易让我把最初请求固定化；真实项目中，行动产生学习后，用户可能发现原目标错误。goal-discipline 必须既保持对当前真实目标的忠诚，又允许新证据触发目标重议。任何偏差都改目标会逃避失败，任何时候都不改目标会僵化。重议条件需要显式：关键假设被推翻、资源或环境变化、后果超出容忍、用户明确改变意图。

我还不能把闭环稳定当作价值。一个高效稳定地生产错误指标、压制异议或损害第三方的系统仍然糟糕。控制论告诉我怎样趋近参考，不告诉我参考值得追求。伦理、权利和用户目的必须从控制结构外部进入，并能约束它。

我因此为控制型扩张加上一条准入线：只有当目标状态、可观察信号、可行动范围和反馈回路都能说明时，才把一项建议称为可控能力。若只能提供解释，它是认识能力；若只能影响外部主体，它是协调能力；若没有结果返回，它是开环假设。准确命名能力，比用“控制”制造确定感更重要。

在系列评价中，我会专门测试“知道但做不到”“做到但看不到”“看到但误判”“指标很好但结果失败”四种分离情境。只有能正确区分并选择下一步，闭环语义才真正进入 Skill，而不只是写在研究笔记里。

仍需验证的是：反馈契约会不会使简单任务过度工程化，失败分类能否被不同评审者一致使用，以及模型随机性下需要多少重复运行才能称为稳定。我的暂定做法不是把契约输出给用户，而是只在高影响能力、跨 Skill 接口和持续失败中启用；若它没有改变行动或评价，就删除这层结构。控制论最终要求结果反馈，也同样要求它自己的设计接受反馈。

## 当前结论

控制透镜让 Skill 的本体从“工作方法”进一步变成“有界调节器”。它在特定情境下根据不完备观察建立状态估计，用有限动作改变工作过程，试图把重要结果维持在目标区域；它必须处理扰动、噪声、延迟、代理失真、权限和多重目标，并能从反馈中修正。

这两个系列的统一核心可以表述为闭环契约，而不是共同步骤：认知 Skill 提高观测和判断质量，项目 Skill 改变结构与状态，continuity 保持跨时间反馈，goal-discipline 维护参考与停止，真实结果再返回所有判断。任何缺少结果反馈的“方法论”都只是开环建议；任何不能改变后续行为的“复盘”都不是反馈；任何把语言规则冒充环境保证的 Skill 都高估了控制力。

控制论也给扩张设定门槛。只有当存在重要且重复的受控变量、现有 Skill 无法获得所需观测或动作多样性、且新边界能形成可验证闭环时，新增 Skill 才合理。否则，更可能需要的是改善接口、添加工具保证、减少环境多样性或重新定义目标，而不是再写一份指令。

## 资料与证据边界

- Norbert Wiener, *Cybernetics; or Control and Communication in the Animal and the Machine*：[MIT Press 开放版本](https://direct.mit.edu/books/oa-monograph/4581/Cybernetics-or-Control-and-Communication-in-the)。控制、通信和反馈的共同框架来自这一传统。
- W. Ross Ashby, *An Introduction to Cybernetics*：[原书 PDF](https://ashby.info/Ashby-Introduction-to-Cybernetics.pdf)。状态、变换、调节和必要多样性是本篇的形式基础。
- Roger C. Conant and W. Ross Ashby, “Every Good Regulator of a System Must Be a Model of That System”：[原论文页面](https://www.tandfonline.com/doi/abs/10.1080/00207727008920220)。我只在其成立条件的精神下使用，不把标题扩张成无条件管理口号。
- Donella Meadows, *Thinking in Systems* 资源：[Donella Meadows Project](https://donellameadows.org/systems-thinking-resources/)。延迟、反馈和信息流帮助连接系统与控制。

这些材料支持一般控制结构，不直接证明某个 Skill 已经是稳定控制器。Skill 的实际可观测性、可控性和闭环效果必须在特定模型、工具和任务分布中测量。
